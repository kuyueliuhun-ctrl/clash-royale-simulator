# 在线口径实测：`p4b` 的优势**不成立**（S2 第四轮，2026-09-18）

> **一句话**：把口径换成**奖励项真正会用的那个**（tick 级、K=30 tick）之后，

## §0 结果（写在前面的那张表）

**数据**：`runs/et_measure/` —— `run` 模式、`economy_etm`（= `economy` + **measure-only**）、
**5 个评估点 × 50 局 = 250 局**（`--steps-per-eval 4000 --total-slog 16000 --only-vs-main --n-eval-games 10`）；
每局都带**在线口径**的逐帧局面明细。取数时间 2026-09-18。

| 配对量（同批内 `p4b − none`） | **在线口径**（本轮，n=250） | 离线口径（第二轮，n=250） | 倍数 |
|---|---|---|---|
| Δρ(终局塔血差) | **+0.008**（sd 0.018，4/5 正） | +0.145（5/5 正） | **÷18** |
| Δρ(胜负) | **+0.014**（sd 0.011，5/5 正） | +0.108（5/5 正） | **÷7.7** |
| Δρ(皇冠差) | **+0.009**（sd 0.021，4/5 正） | — | — |
| 基准 `ρ(none, 塔血)` | **+0.084**（逐批 −0.125 / +0.332 / −0.105 / +0.115 / +0.203） | −0.198（4/5 负，component 口径） | 符号都变了 |
| 基准 `ρ(none, 胜负)` | **+0.240**（5/5 正） | −0.061 | 符号都变了 |

逐批 Δρ(塔血)：`+0.022 +0.010 +0.015 +0.018 −0.023`；逐批 Δρ(胜)：`+0.007 +0.009 +0.018 +0.032 +0.004`。

**读法**（三种都必须说清，不能只挑一种）：
1. **方向一致**：Δρ(胜) **5/5 批为正**（符号检验 p = 0.031），Δρ 的批间 sd 很小（0.011–0.021）
   ⇒ 「`p4b` 加了一点点东西」在统计上是**可复现的方向**。
2. **幅度不可用**：+0.014 的秩相关提升，相对于 n=50/批的 1σ（≈0.143）与任何可判读阈值
   都是**噪声级**；它**不足以**支撑一次 4 小时的 A/B（【R5】）。
3. **与离线口径差一个数量级** ⇒ **上一轮"配对 10/10 正、均值 +0.145"的结论在本轮被量化地推翻**：
   它不是"效应小"，而是**大部分来自口径**（帧采样把一次交战切成大量微窗口，
   而在线把同一段交战合成少数长窗口 ⇒ 同样的 `ΔΦ` 被摊到不同数量的窗口上）。

### 0.1 顺带被推翻的还有"缺口"的符号
离线 **component** 口径下 `ρ(none, 塔血)` 是 **−0.198**（4/5 批为负）——我上一轮据此说
「现行 Φ 偏好"让塔挨打"」。**在线口径下它是 +0.084（3/5 批为正）**、`ρ(none, 胜)` 是 **+0.240**。
⇒ 「窗口化 `Φ` 系统性地偏好挨打」**在真正会用的口径下不成立**；那是 component 口径的产物。

## §1 为什么必须做这一步

上一轮量出的口径分歧（同一局：离线 `identity=core` **67** 个窗口 vs 在线 **2** 个）说明
**离线的窗口划分与奖励项用的不是同一个量**。本轮把口径对齐后重测，得到的正是上面那张表。

**measure-only 的设计要点**：让评估局跑监视器、把每个决策帧结算掉的局面写进录像，
但**一分奖励都不加** ⇒ 行为与不接线**逐位相同**（有回归测试），
因此 250 局的**对局本身**与不做测量时完全一样 ⇒ 可以放心用它做判据。

## §2 实现与 4 个接线坑（都踩过并修掉，值得记）

### 2.1 新增/改动
| 位置 | 改动 |
|---|---|
| `rl/engagement.py` | 逐窗口明细 `phi_part / tau / score / n / tau0 / tau1` + `pop_detail()` |
| `rl/env_wrapper.py` | `engagement_trade_measure_only` 开关；逐帧 `info["engagement_trade_detail"] = [phi, τ, score, n, τ0, τ1]`；开时**不加奖励** |
| `rl/replay.py` | 帧追加**可选键** `et`（缺省 `None`，完全向后兼容） |
| `rl/config.py` | 新预设 **`economy_etm`**（= economy + measure-only） |
| `rl/run_league.py` | `_eval_env(seed, et_measure)` + `_set_et_measure(cfg)` + 评估 worker 显式传参 |
| `scripts/analyze_online_trade.py` | 从 `et` 键还原 main 视角 → 重组 `trade_none`/`trade_p4b` → 同批**配对** ρ |
| `scripts/selftest_engagement_trade_online.py` | 新增 `test_measure_only_is_behavior_neutral`（**2/2 PASS**） |

### 2.2 坑 1：**评估 env 根本不接收 `reward_weights`**
`_play_pair_games` / 评估 worker 里的 `RLEnv(opponent=None, seed=...)` **没有传 `reward_weights`**
（用 `env_wrapper` 的缺省）⇒ 与训练**本来就是两套奖励口径**，而且任何只挂在 `cfg.reward` 上的
开关都**到不了评估局**。代价：第一版测量跑完后录像里 `et` 全是 `None`。
⇒ 修法：加 `_eval_env()` 统一入口。

### 2.3 坑 2：**WSL→Windows python 不传递命令行前缀环境变量**
本想用 `DSH_ET_MEASURE=1 python.exe ...` 做开关。实测：
`FOO_BAR=1 python.exe -c "os.environ.get('FOO_BAR')"` ⇒ **`None`**（换成任何名字都一样）。
⇒ 开关改成**由配置驱动**（`reward["engagement_trade_measure_only"]`）。
（注：harness 自己的 `DSH_*` 变量是另一条通道进来的，不能靠它。）

### 2.4 坑 3：**评估 worker 是 `spawn` 出来的新进程 ⇒ 模块全局会重置**
`_ET_MEASURE` 只在**父进程** `main()` 里被 `_set_et_measure(cfg)` 置位；worker 重新 import 模块
⇒ 全局仍是 `False` ⇒ 评估 worker 里 `_eval_env` 拿到的是**普通 env**。
⇒ 修法：把标志**显式当参数传**（`_eval_pair_worker_main(..., et_measure)` → `_eval_env(seed, et_measure)`），
并**先本地端到端验证**（直接调 `_run_eval_pairs_parallel` 跑 2 局，确认 `et` 落在 360/360 帧上）
**再**开长跑 —— 这一轮为此重启了 4 次。**教训：spawn 架构下"全局开关"必须在子进程入口重放。**

### 2.5 坑 4（★ 跑数据之前发现的真 bug）：**在线 `τ` 也是 p0 视角的**
离线仪器有缺陷 7.3（零和只算 p0 视角 ⇒ 另一半局被系统性扣分）。**在线实现同型**：
只统计"p1 的实体被 p0 的非塔实体钉住"，p1 侧取负 ⇒ main 坐 p1 的那一半局拿到的 `τ`
**与它自己做了什么无关**。
⇒ 在**开跑之前**改成两侧都记（`pin0`/`pin1`）+ **双侧塔血门控**，
`tower_term = (τ₀ − τ₁)/2`（零和且两侧对称）。
**真数据自检**：`τ == (τ₀−τ₁)/2` 在 **54,609 / 54,609 帧**上成立（0 违例）。

### 2.6 顺带：R1 的孤儿检查**这一轮救了 4 次**
我用 `pkill -f` 自杀式匹配、以及 `kill` 错 PID，先后留下 **2 + 12 + 11 个** spawn worker
（约 2.9–7 GB）。每次都是**长跑前的 `check_commit.py`** 报 `[WARN] < 12 GB` 才被发现，
再用 `scripts/kill_orphan_workers.ps1` 清掉（清完 19.30 → **22.17 GB**，档位判回 12 OK）。
⇒ **教训固定下来**：① 不要用会匹配到自己命令行的 `pkill -f`（改用 PID / `taskkill /F /T`）；
② 停跑之后**先**跑孤儿工具**再**看内存。

## §3 判读与门禁

| 门禁 | 判定 |
|---|---|
| **S1** | 未通过 ⇒ 约束在**探索/机制侧**（Xbow 自锁）—— 未变 |
| **S2（本轮的最终答案）** | 在**正确口径**下，唯一候选 `p4b` 的配对提升只有 **+0.008（塔血）/ +0.014（胜）** ⇒ **不足以放行**；<br>且上一轮的 +0.145/+0.108 已被证明**主要是口径产物**（÷18 / ÷7.7） |

⇒ **S3 仍不开。** 而且现在的理由是**关于机制本身**的：
**这条奖励项在它真正会生效的口径下，与"赢/不输塔"的关系弱到不值得花一次 A/B 去测。**

**如果还要继续这条路，必须先回答的问题**（都不是"再跑一个 A/B"能回答的）：
1. **`τ` 的量级问题**：在线口径下 `τ` 的均值只有 `ΔΦ` 部分的 ~1/12（本轮 Στ/Σφ ≈ 54.9/639.7），
   且只有 ~38% 的对局里 `τ≠0`。⇒ **P4b 这个代理本身太稀疏**，不是"权重调小一点"能救的。
   要么换一个有密度的"被阻止的伤害"代理（例如**按塔血轨迹**而不是按"钉住时长"），
   要么承认这一格的信息**在当前可观测状态下提取不出来**。
2. **S1 的机制前置**（Xbow 自锁）：即使奖励项有效，策略也**没有可学的样本**。
3. **尾部窗口缺口**（`max_ep_steps` 截断时局内未结算窗口的 score 全丢）—— 已在
   [`engagement_trade_online_2026-09-18.md`](engagement_trade_online_2026-09-18.md) §5.1b 实测。

**建议**：把这一格**降级为"已取证、不接线"**（`ledger.md` 的 X 系列），
把力气移回 S1 指出的机制侧（`ACE_CARDS`/`SINK_TANK_CARDS` + "只推荐付得起的牌"自锁）。

## §4 局限（【R10】）

1. **n=250 局、5 个批次、1 个 run**（`et_measure`，16k 步、`run` 模式、对手是脚本）
   ⇒ 按【R5】**只是"这个口径下的效应量级读数"，不是判决**；但它足以**否定一个 +0.145 的效应**
   （1.7σ 之外）。
2. **`run` 模式的胜负方差仍然小**（本 run 的胜负分布未逐局统计）⇒ Δρ(胜) 的解释力有限；
   真正的判据仍应挂在 `solo`（预注册 §8）。
3. **measure-only 只测了 `p4b` 与 `none` 两个变体**（同一批局里重组出来的）；
   `p3b/p1/p2` 未在在线口径下重测 —— 但 `p3b` 已被证明是已有击杀项的重新加权、
   `p1` 量纲失控且 5/5 批 ρ 为负，**没有理由期待它们在在线口径下翻身**（**未验证**，如实标注）。
4. **`τ` 稀疏的原因未逐案归因**（是"钉住"不常发生，还是 `cost(E)` 常为 0，还是门控常被关掉）
   ⇒ 只报了 Στ/Σφ 与 `τ≠0` 占比两个量。
5. 本轮的 4 次重启说明**接线仍未做过"全链路 dry-run"**；已用
   `_run_eval_pairs_parallel` + 2 局的本地端到端验证补上（见 §2.4），但那只覆盖评估路径。
