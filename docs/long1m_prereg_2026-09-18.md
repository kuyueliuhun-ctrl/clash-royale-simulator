## 1. 为什么要跑

用户（2026-09-18）指示：

> 「跑一个100万步训练，8000步一次评估」
> 随后改为两级评估：「我们不要评估40次，那太多了，我们可以把评估分为大小评估，
> **10w步一次大评估，其余小评估，小评估10\*5次，大评估20\*5次**」

背景（本会话已确证的上下文，不再重复）：run 模式是 2026-09-17 用户选定的主线
（`--mode run`：5 个脚本 agent + main + Elo，见 [`docs/run_mode_multideck_2026-09-17.md`](run_mode_multideck_2026-09-17.md)），
且该文件 §4 已披露：**对手全是 mask-随机脚本**（无自对弈、无防守脚本、无 frozen/hist 池）。
本轮的目的不是"证明 run 模式更好"，而是**把这个主线的 1M 步长跑真正跑出来**，
并把曲线分辨率/噪声的取舍写死在预注册里。

**为什么必须有这项工程改动**：run 模式的评估原本**串行**（`eval_round_robin` → 逐 pair 逐局），
且**完全忽略 `--eval-workers`**。实测单局 ≈ 8~10 s（纯 Python 引擎模拟，1 决策帧 = 30 tick）⇒
本计划的 7 100 局 = **17.8 h 纯串行评估**，比 1M 步训练本身（≈10.1 h）还贵。
故本轮同时落地：① 两级评估调度；② run 模式评估并行分片（默认仍是串行，见 §5）。

## 2. 变量与不变项

| 项 | 值 | 说明 |
|---|---|---|
| **变量 1（用户指定）** | `--total-steps 1000000 --steps-per-eval 8000` | 小评估网格 8 000 步 |
| **变量 2（用户指定）** | `--big-eval-every 100000 --n-eval-games-big 20` | 大评估网格 100 000 步、20 局/对 |
| **变量 3（用户指定，折算）** | `--n-eval-games 10` | 小评估 10 局/对。「10×5 / 20×5」的 5 = 5 个对手对（`only_vs_main`） |
| 模式 | `--mode run`（2026-09-17 用户选定主线） | 5 脚本 agent + main + Elo |
| 预置 | `--config economy` | 与 §2.2 标准协议同源（`gae_lambda=0.99`、`value_norm=running`、`value_bypass`、`value_independent`、`only_vs_main=True`、`ppo_epochs/minibatch/shuffle` 见命令行） |
| `only_vs_main` | `True`（economy 预设自带；命令行亦显式） | 评估 5 对而非 15 对。**语义**：PFSP 采样权重只取决于 `(main, 对手)` 的胜率 EMA（`rl/pfsp.py:weights`）⇒ main 的对手分布不受影响，省掉的只是非 main 对之间的 Elo/展示统计 |
| `n_envs` | `1`（默认） | **刻意不动**：`--n-envs>1` 会改 PPO 批的组成（跨 env 交错）= 另一个变量；冒烟基线 `run_smoke5` 也是 `n_envs=1` |
| `--eval-workers` | `12`（**显式**） | run 模式评估并行分片（R1 经验档位 12；worker 屏蔽 CUDA，纯 CPU 推理） |
| `--device cuda` / `--diagnose-every 10` | 同标准协议 | 诊断每 10 次更新采样一次 |

**与冒烟基线的可比性**：`run_smoke5`（600 步 / 3 点 / 60 局 / 1228.7 s / EXIT 0）用的是
`standard` 预设 + 全轮转（15 对）+ 串行评估 ⇒ 本 run 与它差 3 处（预置、only_vs_main、评估并行度）。
**本 run 不与任何历史 run 做单变量对比**，只读它自己的曲线与机制指纹。

## 3. 开跑前的成本标定（脚本可复算）

| 量 | 实测值 | 来源 |
|---|---|---|
| 训练吞吐（run 模式，`n_envs=1`） | **27.4 步/s**（2000 步 / 73 s） | `runs/cal_1m`：`main_ckpt_0.pt` 01:22:51 → `main_final.pt` 01:24:04 |
| 串行评估单局 | **≈8.3 s/局**（60 局 ≈ 500 s） | 同上：启动 01:13:33 → `league_0.pkl` 01:22:51（含启动 ≈58 s） |
| 1M 步训练 | **≈10.1 h** | 1 000 000 / 27.4 / 3600 |
| 评估点/局数 | **131 点**（大 11 / 小 120）= **7 100 局** | 2000/8000 两网格并集：126 + (11−6)；局数 (120×10 + 11×20)×5 对 |
| 串行评估总时长（若并行失效） | **≈33.5 h** | 见下方「⚠️ 更正」：`only_vs_main` 下**每一局都是模型局**（大/小点各 ≈17 s 串行）⇒ 120×850 + 11×1700 s |
| 并行评估总时长（12 worker） | **≈5.7 h** | 实测 大点 **294.3 s** / 小点 **142.8 s** ⇒ 120×142.8 + 11×294.3 s（≈6× 加速） |

> **⚠️ 更正（2026-09-18 01:50，开跑后 13 分钟，仅依据 `eval@0`/`eval@8000` 两个已完成的评估点）**：
> 本节原来的「单局评估 ≈8.3 s ⇒ 串行 17.8 h / 并行 2.2 h / 总 12 h」是**错的口径**——
> 那个 8.3 s 来自标定跑 `cal_1m` 的**全轮转**平均（15 对 × 4 局 = 60 局里只有 **20 局**含模型、
> 跑在 GPU 上，另 40 局是纯引擎的 bot-vs-bot）。本 run 用 `only_vs_main` ⇒ **5 对全部是 main 局**，
> 逐局成本 ≈17 s（父进程 GPU 推理）而不是 8.3 s。**并行侧的实测**：`eval@0`（大点，100 局）
> **294.3 s**、`eval@8000`（小点，50 局）**142.8 s**，与「每 worker 串行 ≈33 s/局 + spawn ≈8 s」的
> 两点外推一致；同期用 PowerShell 采样 12 个 worker 的 CPU **各 ≈100~120% 单核、合计 ≈12.8/16 核**
> ⇒ **不是线程超订**，而是 worker 侧模型走 CPU（父进程走 GPU，故 worker 单局比父进程慢 ≈2×）。
> **结论不变（并行仍有 ≈6× 收益、且这是该模式唯一的可行路径）**，但预计总墙钟改为
> 训练 **10.2 h**（实测 27.3 步/s，含 4-epoch PPO 预算）+ 评估 **5.7 h** ≈ **15.9 h**
> （若并行失效降级串行则 **≈43.7 h**）。判读时以 `docs/train_long1m.log` 里逐点的
> `[eval@N] 完成：… 用时 Xs（并行 worker=12）` 复算，不得沿用本表的任何估计值。

### J2 —— critic / 训练健康（run 内自对照，不作为"变强"证据）

| 读法 | 通过条件 |
|---|---|
| 价值通道活着 | 131 点里 `h_std > 0.05`、`n_abs < 0.9` 的占比 ≥ 90%（阈值来自 `rl/diagnostics.py` 既有门槛，不新标定） |

### J3 —— 绝对强度读数（本 run 唯一的非自引用指标）

run 模式的评估对手是**固定脚本池**（5 个 mask-随机 agent，不学习、不演化），
轮内聚合 Elo（`_round_estimates`）因此是**相对固定仪器的绝对强度读数**——
这是本项目第一次拿到**非自引用**的强度曲线（solo 的"打冻结副本/打上一评估点"全部失真，见 §3 判读禁则）。

| 读法 | 判定 |
|---|---|
| 主判据 | **末 3 个大评估点（800k/900k/1000k）的 main 轮内估计 Elo 中位数** − **首 3 个大评估点（0/100k/200k）中位数** |
| 判决门槛 | \|Δ\| ≥ **71 Elo** ⇒ 记 **P-UP**（Δ ≥ +71）/ **P-DOWN**（Δ ≤ −71）；其余记 **P-FLAT**（不可区分） |
| 阈值来源（脚本可复算，非手抄） | 【R16】要求阈值 ≫ run 间散布且不来自单次观测。这里由**解析式**给出：大点每对 20 局、`only_vs_main` 下 main 参与 **5 对** ⇒ `games_main = 100`，`SE_point = 347.5/√100 = 34.8 Elo`（`_round_estimates` 的既有公式）；3 点**中位数**的 SE ≈ `1.253 × 34.8/√3 = 25.2`；两个中位数之差的 `SE_diff = √2 × 25.2 = 35.6` ⇒ `2σ = 71 Elo`。判读时须用脚本从 `league_state.json` 复算 `games_main` 与 SE（若与 100 不符以脚本为准并更正本条） |

**三个分支都要如实记录**：`P-UP` = run 模式在 1M 步内产生了对固定脚本池的可测强度提升（第一次非自引用证据）；
`P-FLAT` = 1M 步在 run 模式（弱对手、无自对弈）下不产生可测提升 —— 与【未决 O1】（绝对强度不动）
及"**模型连局部最优都做不到**"并列；`P-DOWN` = 退化，需归因（不许只写"退化了"）。

### J4 —— 行为门禁（只记录，不阻断）

`league_state.json` 的 `gates`（engagement ≥ 50%×首点、ghost ≤ 2×首点）逐点记录；
**绝对数不跨 run 比**（【否证 X9】），只读**相对本 run 首点**的退化。

## 5. 本次改动引入的"静默失效"清单（每条都配了会失败的回归测试）

| 风险 | 症状 | 防线 |
|---|---|---|
| CLI flag 没进 overrides 元组 | `--big-eval-every` 传了不生效，曲线噪声不变而你以为变小了 | `test_eval_scheduler_two_tier` ④（源码级断言 + 覆盖） |
| 大评估网格被小网格吞掉 | 100k 的大评估点根本不存在（8000 ∤ 100000），你只会看到"两边一样吵" | 同上 ③（并集断言：131 点、100k/300k/500k/700k/900k 被插入） |
| 大评估预算没传下去 | 大点静默退化成小预算 | 同上 ⑤（打桩 `eval_round_robin` 断言 `n=10/20`） |
| rescue resume 后重复评估同一格点 | 曲线出现重复点/双点（历史 10e 踩过） | 同上（`_EvalScheduler(cfg, 8000).due(8000) is None`） |
| run 模式评估并行**改变 league 状态演化** | Elo/PFSP 与串行不同 ⇒ 曲线不可比 | `test_eval_round_robin_parallel_equivalence` ②（`n_games=1` 时并行==串行，Elo + 录像数逐位一致） |
| **`--eval-workers` 默认值把 run 模式从串行变成 16 进程** | 所有既有 `--mode run` 命令默认行为改变 | `main()` 里显式区分：**只有显式传 `--eval-workers` 才并行**，否则 `cfg.eval_workers=1`（逐位回旧行为） |
| 策略对象过不了 spawn pickle（`ScriptedPolicy.env` 指向 env） | worker 启动即崩 / 拖整个 BattleState | `_policy_spec` 只传重建所需最小数据；⑤ 之外另测 spec 往返（含 economy 架构标志） |

## 6. 不判什么（防止跑完现编）

- **不判**小评估点（10 局/对）的单点胜率/Elo 波动：小点 SE ≈ 49 Elo（25 局/对 ⇒ 347.5/√125），
  单点差分噪声远大于任何真实趋势 ⇒ 小点只提供**形状**（相位/塌陷是否持续），不提供判决。
- **不判** main vs 单一对手的胜率是否"赢多输少"。
- **不判**与历史 solo run（`nostall20k`/`d1_long_100k`）的任何数值对比：模式、对手池、
  评估仪器全不同。
- **不判** `gates.json` 的绝对阈值。
- **不判**"run 模式优于 solo 模式"——本 run 没有 solo 对照组。

## 7. 异常处置（【红线 R1】）

任何性能异常（吞吐骤降 / 子进程批量崩 / `WinError 1455` / spawn 失败 / 评估卡死 / 进程莫名退出）：
**先暂停留证、归因外部、等人类**；**不自动降级、不为绕开它改代码或下调配置、不把猜测写进注释**。
成因未定就写"未定"。判读任何性能数字前先确认本次有没有发生降级
（⚠️ 本 run 的评估并行**自带**降级路径：worker 失败 ⇒ 串行重算，这是**设计内**行为，
但它会把墙钟从 ~12 h 拉回 ~28 h，故必须在 J1 里如实记账）。
