1. **全帧圣水 ≥6 占比** = 全部帧（**含不出手的帧**）里 `frame["elixir0"] ≥ 6` 的比例；
   分母 = 被测策略（player-0）全部帧数。`elixir0` 是「本帧动作已扣费 + 本步 0.5 s 回复已计入」的读数

3. **部署前圣水中位** = 只取「**恰好 1 个去重子动作**」的帧（此时 `pre = post + 卡费` 精确），

4. 附带 prereg §3 第 4 列：**同路两次部署间隔中位**（`t` 差分，同路 = 本地 `x<9` 判路）。
5. `step` = 决策帧（【R9】）；本门禁**不成立任何胜率判据**，得分/胜负只作背景（prereg §3 已禁）。

## §4 判决

### 4.1 按 prereg §5 的表二选一

prereg §5 原文判据（一字不改）：

> | 手写专家能做到「攒费 → 打 Xbow」（如全帧圣水≥6 占比 ≫ 0.11%，Xbow 出手 ≫ 0.03%） | 约束**在结算/优化侧** |
> | 手写专家**也做不到** | 约束**主要在探索/机制侧**（动作空间、plan 通道、掩码），**不是奖励结算** |

预注册指定的仪器 = `BeliefPlanner` ＋ **PlanToken 贪心执行器**。最忠实的转录就是臂 `token_strict`
（token 建议哪张打哪张、`hold_mask`/`elixir_budget` 生效、落点由 `placement_hint`/`focus_region`
折算并在掩码内取最近格）。它的读数：

- ① 全帧圣水≥6 = **0.000000（0/8191）**，基线 0.0011 ⇒ **≈0，不 ≫**（连基线都没到）；
- ② Xbow 出手率 = **0.000000（0/929，95% 上界 0.32%）**，基线 0.0003 ⇒ **不 ≫**（0 < 基线点估计）。

两项都不满足 ⇒ **未通过（不显著 ≫ 基线）** ⇒ 判决 = **约束主要在探索/机制侧，不是奖励结算。**
（即「结算改动暂停、S3 不做」。）

**为什么不能判「在结算侧」**：判「在结算侧」需要**同时**满足 ①②；这里 ② 是**严格 0**，
且是在**对被测臂最宽松**的参照（拿更高的历史值 0.11%/0.03% 当门槛）下仍然 0。
按 prereg 的失败分支，此时**不得**写成"只差结算"。

### 4.2 执行器能力上限（必须交代，否则上面这句会被过度解读）

我的执行器**不是**一个完整的 CR 专家，它的上限写在脚本 docstring 里，逐条列出：

| 能力 | 有没有 | 说明 |
|---|---|---|
| 攒费（hold） | **纯 token 臂：只有 token 说 hold 才 hold** | `save_ace`/`setup_wait` 才置 `hold_mask`；这两个意图在 **Xbow 卡组上从不触发**（见下） |
| Xbow 落点/时机逻辑 | **纯 token 臂：没有** | 落点只由 `placement_hint`/`focus_region` 折算；没有任何按卡名的战术 |
| 同刻多卡协同（`bundle_size_hint`/`combo_hint`） | **没有**（两臂都没有） | 每帧最多 1 个子动作 ⇒ 实测 `dup_subaction_frames=0`、`n_subactions == n_subactions_dedup` |
| 精确目标选择（`target_kind`） | **没有** | `target_kind` 未参与转录 |
| 圣水预算（`elixir_budget`） | 有 | 单卡费 > `elixir_budget×10` ⇒ 本帧不出 |
| 掩码/整包校验路径 | **有**（强制） | 落点全部取自 `mask["cells"]`，且过 `validate_bundle`；非法计数见 §3D |

**关键机制事实（读码 + 本脚本计数证实，`token_strict` 20 局 / 8191 帧）**：

1. Xbow **既不在** `rl/plan_space.py:ACE_CARDS`（= `Lightning/Vines/Freeze/Rocket`），
   **也不在** `rl/belief_planner.py:SINK_TANK_CARDS`（沉底血牛名单）⇒ `_save_ace` / `_setup_wait`
   这两个**唯一会置 `hold_mask` 的意图**在 Xbow 卡组上永不命中：
   实测 8191 帧里 `setup_wait` = **0 帧**、`save_ace` = **0 帧**（执行器意图直方图，见臂 JSON）。
2. `_pick_suggested_card`（`rl/belief_planner.py:263-288`）只从**当前付得起**的手牌里挑
   （`if p.elixir < Card(card).elixir: continue`），而 Xbow 要 **6 费**。
   纯 token 转录的执行器**每帧把圣水花到见底**（实测全帧圣水中位 1.536、max 4.179、
   ≥6 = **0/8191**）⇒ **Xbow 连"候选"都进不去**：
   脚本计数器 `suggested_xbow` = **0**（20 局 8191 帧里，token 一次都没建议过 Xbow）。
   ⇒ 这是一个**自锁回路**：不攒费 ⇒ Xbow 不可负担 ⇒ 规划器不推荐 Xbow ⇒ 继续花小费牌。
3. `token_strict` 的 Xbow 出手 = **0/929** 因此是**结构性零**（不是抽样不足）；
   其 95% 上界 0.32% 仍与基线同量级，故判"不显著 ≫"。

⇒ **因此臂 `token_strict` 的失败只能证明「用 `BeliefPlanner` 现有的 PlanToken 语义做不到」，
不能推广成「此环境下手写专家做不到」。** 后者由下面的探针直接否证。

### 4.3 能力上限探针（臂 `token_xbow`）：证明约束**不在动作空间/掩码**

`token_xbow` = `token_strict` ＋ **一条手写规则**（脚本里写在明处）：
非紧急帧（我半场无敌军 且 token 不是防守/解牌意图）里

- 手牌有 Xbow：`elixir < 6` ⇒ **不出牌（攒费）**；`elixir ≥ 6` ⇒ **下 Xbow**（压血量更低的敌方公主塔那一路，本地 `y=14`，即最靠河的己方合法格）；
- 手牌无 Xbow：打**最便宜的合法牌**过牌（把它轮进手牌）。

这条规则**不在 `PlanToken` 语义里**，所以它**不能**当作 prereg 仪器的结果；它的作用只有一个：
**给「手写专家能做到吗」这句话定上界**。读数：

- Xbow = **47 次 / 1003 次出手 = 4.686%**（**156×** prereg 参照 0.03%；95% CI ≈ [3.5%, 6.0%]），**18/20 局**出现过 Xbow；
- 47 次 Xbow 的**部署前圣水**：中位 **6.25**、min **6.1786**、**100% ≥6**（`forensics_card_usage.py` 独立复算：6 费档「可达窗口」= 0.005269，与全帧≥6 一致）；
- ① 全帧圣水≥6 = **0.005269**（**4.79×** 参照 0.11%），**48/9110 帧**。
  它只有 ~5× 而不是量级差的原因**已定位**：攒到 6 就在下一个合法帧把 Xbow 打出去，
  ≥6 状态是**瞬态**（"攒费→兑现"而不是"攒着不动"），所以这个代理指标的绝对值上不去；
  真正直接的口径是上面的「Xbow 部署前圣水中位 6.25 / 100% ≥6」。

⇒ **可执行路径存在且合法**（47 次全部通过掩码与整包校验、引擎 0 拒绝、落点全部 ≤ 本地 y=14）。
⇒ prereg 表第二行括号里点名的「**动作空间**、**掩码**」被**证伪**为约束点；
剩下的是「**plan 通道**」＋ 探索侧：`PlanToken` 的意图表里没有任何一格表达
"用终结建筑/赢牌手段"，`ACE_CARDS`/`SINK_TANK_CARDS` 两张名单把 Xbow 排除在外。

### 4.4 判决的准确措辞（避免含糊）

- **对 prereg 指定的仪器**：**未通过（不显著 ≫ 基线）** ⇒ 约束**主要在探索/机制侧**（非结算侧）。
- **机制侧的定位**：**不是**动作空间/掩码（§4.3 已证伪），**是** plan 通道（`PlanToken` 不表达赢牌手段）
  ＋ 探索侧（`_setup_wait` 的沉牛门槛/`ACE_CARDS` 名单把 Xbow 排除）。
- **不得**把 §4.2 的失败写成「手写专家做不到」；正确的写法是「**用现有 PlanToken 语义做不到**」。

## §5 冰人白嫖推论：**证实**（带相位限定）

**被验证的推论**（`docs/frame_credit_proposal_review_2026-09-18.md` §7.8 第 2 条登记为"未做数值验证"，
同文件 §7.1 下半格的算式）：

> 拉扯 → 拖住/换节奏，没打死：冰人/骷髅被吃掉 ⇒ 对方 `V` 不变、我方 `V` −2 ⇒ **Φ −2 ⇒ 奖励 −1.0**。

**仪器**：`scripts/phi_offline_check.py`（离线逐帧重建 `_v_share` 台账 + `_active_v` + `dΦ`）。
**证据路径**：`docs/phi_offline_check_run100k.json` / `_schema4.json` / `_long1m.json`
（＋同名 `.log`；命令见 §1 第 5 条）。

### 5.1 结论：**证实**（`edw=0.5` 即 `t<120 s` 时精确 −1.0；双倍期是 −0.2）

| 数据集 | schema | 局 | 帧 | IceGolemite 实例（出现 / 见到死亡帧） | 端到端 `ΔΦ` | `edw×ΔΦ` = −1.0 占比 |
|---|---|---|---|---|---|---|
| `runs/run100k/replays`（--max-files 2） | **4** | 150 | 35979 | 23 / **10** | **全部 = −2.000000** | **100%**（10/10，死亡全在 t<120） |
| `runs/run_schema4/replays` | **4** | 60 | 18705 | 123 / **58** | **全部 = −2.000000** | 43.1%（25/58，其余 33 例 = −0.2） |
| `runs/long1m/replays`（任务书原路径，实为 schema 3） | 3 | 1000 | 195851 | 77 / **34** | **全部 = −2.000000** | 85.3%（29/34，其余 5 例 = −0.2） |

- v1 的两半："`Φ` 净 **−2 费**" —— **证实**：**102/102** 个「见到死亡帧」的真实实例
  端到端 `ΔΦ = (-cost + 部署份额) + (-死亡注销) = −2.000000`（min = max = −2.0，零散布），
  其中 `cost = Card("IceGolemite").elixir = 2.0`（引擎同一张表）。
- v2 的"奖励 **−1.0**" —— **证实但带相位限定**：奖励的 edw 项 = `edw(t_death) × ΔΦ`；
  死亡发生在 `t < 120 s` 时 `edw = 0.5` ⇒ **恰好 −1.0**（-1.0 至 1e-9）；
  死亡发生在双倍期（`t ≥ 120 s`）时 `edw = 0.1` ⇒ **−0.2**。
  ⇒ 原文的「−1.0」应补一句**前提**：**`t < 120 s`（前段费贵）**。
- 证据链②（"这个 −1.0 真的在 reward 里吗"）：死亡帧的**逐帧对账残差**（见 5.2）
  在 `run100k` 上 `|resid| < 0.01` 占 90%、`run_schema4` 占 96.6%。
- 未验证的部分：原文的"**没打出任何伤害**"这一前提**本脚本没有验证**（离线无法可靠判定冰人死亡新星是否命中敌方）。
  但 **Φ 的记账与伤害无关**（只看出牌花费与实体生死），所以"被白嫖"这个措辞的**Φ 部分是精确的**，
  "打不出伤害"只是对该局面的事实描述，不影响 −1.0 的算术。

### 5.2 逐帧 `ΔΦ` 与回放 `reward` 的对账（含用了哪些项、误差多少）

复算口径（写死）：`recon_core = crown + tower(差异化定价/lv11锚) + edw×dΦ + unit_dmg(−k) `，
`resid_core = reward − recon_core`；`edw`/`tower` 直接 **import** `rl/env_wrapper._phase_weights` /
`_per_tower_norm_dmg`（单一来源，不重写）。

| 数据集 | 非末帧 `resid_core` <1e-6 | 非末帧 <0.01 | mean_abs | 「无塔伤/无单位伤」帧 <1e-6 | 「有塔伤/有单位伤」帧 <1e-6 | 花费交叉核对 <1e-6 |
|---|---|---|---|---|---|---|
| `run100k`（schema 4，150 局） | **70.4%** | **92.8%** | 0.0423 | **98.86%**（n=9592） | 59.9%（n=26237） | **98.89%** |
| `run_schema4`（schema 4，60 局） | 53.2% | 94.3% | 0.0280 | 98.16%（n=3696） | 42.1%（n=14949） | 98.51% |
| `long1m`（伪 id，1000 局） | 49.2% | 69.1% | 0.0716 | 98.40%（n=49592） | 32.4%（n=145259） | 99.03% |

**误差归属（已定位的部分）**：

1. **严格相等的缺口主因 = 回放把 hp/坐标 `round(…, 1)`**（`rl/replay.py:127-133`）。
   证据：把「本帧既无塔伤也无单位受伤」的帧单独拿出来（这些帧的复算里没有任何被取整的 hp 进去），
   严格相等率升到 **98.2~98.9%**。⇒ `edw×dΦ` 项**不含 hp**、与 reward 的对账是**精确**的。
2. **末帧单列**：`resid_core` 在末帧取值集中在 **0** 与 **±10**（`run100k`：−10 有 49 帧、+10 有 39 帧、0 有 14 帧）。
   成因：`_run_side0` 走满 `max_steps` 时 `winner` 事后由 `timeout_winner` 判，
   那一步 `env.step` 的 `winner is None` ⇒ reward 里**没有**终局项；引擎在步内 `game_over` 时才有。
   回放不记录 `game_over` 时刻 ⇒ **末帧无法离线判归属**，故主对账只用非末帧。
3. **花费交叉核对**（`Σ卡费` vs `elixir0` 差分 + 逐步回复量反解，回复量按引擎
   `2.8 / 1.4 / 2.8÷3` 精确积分）：**98.5~99.0%** 的帧严格相等
   ⇒ "哪张牌真的被扣了费"这一环是干净的；不等的少数帧 = 引擎死亡圣水馈赠（ElixirGolem 家族）−
   记录了牌但引擎没执行的帧。
4. **`long1m`（schema 3）多出来的误差：成因未定（登记为不确定）**。
   候选：① 回放无实体 `id` ⇒ 本脚本用 (name, player) + 最近位置**贪心匹配**合成 id，
   同刻场上多只同名单位（Skeletons/Minions/Bats）可能配错 ⇒ 生死归属错 ⇒ `dΦ` 错；
   ② 未按 `meta.side0=="main"` 过滤（`long1m` 是 run 模式多卡组，player-0 常是随机卡组 agent）。
   两者都**不影响** §5.1 的冰人结论（该卡同刻通常只有一只，且三个数据集的 `ΔΦ` 都是精确 −2.0）。

## §6 局限与不确定【R10】

1. **样本量**：每臂 **20 局**（任务书建议 ≥20；单进程 6~7 min，受"不长于 ~10 min"约束）。按 40 局
   `1σ≈0.078`（`docs/agents/metrics.md` §3）的噪声地板，**20 局只够看大效应**。
   但本门禁的判据是**行为层计数**而非胜率：`token_strict` 的 Xbow = **0/929 次出手**
   （95% 上界 0.32%），`0` 不是噪声问题；`token_xbow` 的 47/1003 也不是。
2. **胜率不作判据**（prereg §3），本文件里的得分只是背景（20 局 1σ≈0.11）。
3. **对手只有一种**：`SelfDefenderPolicy(passive_prob=0.6)`（真防守脚本）。
   没有跑冻结 checkpoint 臂 ⇒ 不能排除"换对手会改读数"；
   但攒费/出手都是**我方单侧**行为，对手只影响能否攒得住（§3C 显示 47/47 都攒到了 ≥6）。
4. **同批局是"同种子 + 同对手实现"，不是"相同状态轨迹"**：三臂策略不同 ⇒ 状态不同。
   配对只到 `reset/opponent` 种子的层面。
5. **执行器能力上限**（§4.2）是**本门禁最大的解释边界**：它不含多卡协同、不含 `target_kind`、
   不含任何 Xbow 战术；`token_xbow` 的规则是我手写的、不在 token 语义内。
   因此本门禁能回答"**PlanToken 语义下能不能**"，**不能**回答"任何手写专家能不能"。
6. **`long1m` schema 3 的伪 id 匹配**误差未逐帧归因（§5.2 第 4 条）。
7. **`run100k` 是正在跑的 run**（`docs/run100k_2026-09-18.md`）：我读的
   `runs/run100k/replays` 是它的**只读快照**，文件数会随评估点增加（文档里已钉死 `--max-files 2`
   = `league_0.pkl` + `league_8000.pkl`，这两个文件不会再被重写）。
   **未经许可**没有改任何源码、没有起训练、没有动它的 ckpt。
8. 本门禁**未做**：任何训练、任何奖励改动、任何结算侧实验（prereg §5 要求 `S3` 暂停）。
