## 1. 训练现存问题（按严重度）

### 1.1 【实锤·最高优先】评论家损失主导更新，策略实际上被"冻住"

**证据（已复核，主会话从原始日志统计）**

| run | 日志行数 | gnorm 中位 | gnorm 最大 | value_loss 中位 | value_loss 最大 | clip_frac |
|---|---|---|---|---|---|---|
| economy_9j (100k) | 794 | **6,803** | 33,515 | 48.2 | 660.4 | 0.0% |
| economy_9k (20k) | 153 | **5,734** | 31,260 | 38.8 | 443.8 | — |
| economy_10d (12k) | 92 | **9,692** | 40,553 | 56.5 | 380.9 | — |
| economy_9k_ft (12k) | 123 | 数百–14,000+ | 14,207 | 3.5–158 | 158.5 | 0.0% |

- `gnorm` 是 `clip_grad_norm_()` 的返回值 = **裁剪前的总梯度范数**（`rl/ppo.py:121`），
  而阈值 `max_grad_norm=0.5`（`rl/ppo.py:26`）→ 每次更新把梯度整体缩放约 **1.4 万倍**。
- `clip_frac=0.0%` 是 PPO 重要性比率的裁剪比例（`rl/ppo.py:126`）→ **策略比率从未离开
  [0.8, 1.2] 区间**，即策略 logits 每步位移小到不可测。
- 9k_ft 日志 91 个 `ratio=` 实测：min 0.992 / p50 **1.000** / max 1.006，`policy=-0.0002 ~ 0.0011`。
- 同期 value_loss 中位 39–57 ⇒ 评论家 RMSE ≈ 6–7，而单步奖励量级仅
  `0.001×3052 ≈ 3`（`rl/config.py` tower_dmg_opp=0.001 + normalize_tower_dmg）
  → **价值误差与信号同量级，评论家根本没拟合上**。

**口径校正（重要，勿照抄子代理原话）**
严格说，`clip_grad_norm_` 是全局等比缩放，且 Adam 对梯度尺度近似不变（update ≈ lr·m̂/(√v̂+ε)），
所以"裁剪本身把策略学习率打死"这个因果链**不成立**。真正成立的是：
评论家损失量级（MSE ~40–60）远大于策略损失，二者共用一个优化器与一个全局梯度，
**更新方向被价值拟合主导**；`clip_frac=0` 是"策略动不了"的表征而非原因。

**修法（低成本、标准做法，建议优先 A/B）**
1. 价值目标归一化：return/value 标准化或 PopArt（最标准）；
2. 价值损失裁剪（clipped value loss，PPO 标配）；
3. 降低 `vf_coef`（当前 0.5）并单独给 critic 参数组设更高 lr；
4. 复现实验口径：同 ckpt、同种子，只改一项，跑 20k 步看 `clip` 是否离开 0%、
   `value` 是否降到个位数——**这是全项目最便宜的一次高收益实验**。

### 1.2 【结构性·未修】攒费/组波在奖励上是零收益

`elixir_diff` 是 potential-style shaping（`rl/env_wrapper.py:245-253`），下牌瞬间
`E−c` 与 `V+c` 同帧抵消 ⇒ **攒费本身零奖励**；`tower_dmg` 账面上"一波 8 费换塔"与
"四次 2 费换塔"等价。`AGENTS.md` 已诊断（修复方向 B 凹形定价）但**至今未落地**。
实测佐证（已复核）：`deploy=5.5%–10.9%`、`bundle=0.05–0.11`（bundle 均值 <1.2 张）。

### 1.3 【中·结构性】`adv_norm="batch"` 仍在生产配置上

`rl/config.py:104` 默认 `batch`，且所有活跃 run 的 `config.json` 都是 batch。
本项目自己的注释（`rl/ppo.py:73-74`）已说明 batch 中心化会把躺平局的零优势帧
**抬成伪正优势**，强化 STOP。→ 切 `scale`（只除 std、保留符号），一行改动。

### 1.4 【已复核·降级为 P2·防御性】僵局早停的 bootstrap 口径

子代理报告称这是"正确性 bug"（`rl/train_solo.py:963-965` 用 `last_value=0.0`，
而正常截断 `:1013-1017` 用 `main.value(...)`）。**主会话复核后判定该结论不成立**：

早停分支在调用 `compute_gae` 之前，已经把完整终端结算补进 `ep_rew[-1]`
（`:953-962` 按 `timeout_winner` 给 win_bonus / lose_penalty / draw_penalty），
即该帧就是**真实终止帧** → `next_val=0.0` 语义正确，不是低估。
正常截断路径用 `main.value` 是因为那里 `virt is None`（真平、需继续）才需要 bootstrap。

**残留的只是写法脆弱**：`ep_term[-1]` 未显式置 True，正确性隐式依赖
`compute_gae:60` 在 `t==T-1` 必然截断 GAE 累积这一实现细节。
→ 建议显式 `ep_term[-1] = True`（防御性，零行为变更），**优先级 P2，不是 P0**。

### 1.5 【中·结构性】热启动 run 的对手池退化（新发现）

9k_ft 日志第 2 行（已复核）：
`对手池: 无历史 ckpt（本目录首轮训练），退化为 frozen=0.875 / defend=0.125`
→ 设计上的 `70/20/10`（`train_solo._OPP_MIX`）在**热启动 run 里退化成 87.5/12.5**，
PFSP 历史槽为空。而热启动恰恰是当前推荐的训练方式（hint 需热启动才吸收）。
→ 修法：热启动时显式注入外部历史 ckpt（如旧 run 的 `solo_main_*.pt`）填充 PFSP 槽。

### 1.6 【中·结构性】70% frozen 镜像自对弈的共进化

`train_solo._OPP_MIX` = frozen 0.7 / hist 0.2 / defend 0.1，活跃管线全是 solo 镜像。
单策略镜像自对弈天然非传递（AGENTS 已记"winrate 0.5 不代表没进步"）。
`flow_league` 的 6 模型全配对（main/push/counter/lockdown/all/random +
`MODEL_REWARD_OVERRIDES`）**已实现但从未作为活跃训练管线启用**。
→ 把 9k_ft 这类行为已改善的 main 推入多策略池做跨流派验证。

### 1.7 【中·结构性】K_MAX=4 空转 + STOP 静态偏置

`action_bundle.py:28 K_MAX=4`，但 `bundle` 均值 0.05–0.11（≈94% 纯 STOP 帧）；
`follower.py stop_logit_bias=-1.0` 是**状态无关常量**（无条件加在 STOP logit 上），
与该攒费的时机无关 ⇒ 与问题 1.2 叠加，结构性抑制"攒费→泄波"。
→ STOP 偏置改为按圣水水平门控。

### 1.8 【工程】评估默认串行

`rl/config.py:122 eval_workers=0`（串行）。AGENTS 实测：16 局 eval@0 串行 857s vs
16 worker ~240s。长 run 必须显式传 `--eval-workers 16`，忘传就是数量级损失。
→ 默认值改为 ≥8。

### 已确认不再是问题的（勿重复投入）

## 2. 评判指标审计

### 2.1 在用指标盘点（已复核落盘口径）

| 指标 | 位置 | 实际衡量 | 分辨率 | 失效条件 |
|---|---|---|---|---|
| solo 自对弈胜率 | `train_solo.eval_solo` | main vs 当前冻结副本 | N=16 → **2σ≈±0.25** | **自对冲恒定 ~0.5，同步变强时无意义** |
| 对照胜率 vs baseline0/prev | `train_solo._controls_history` | 跨段进步 | 同上 ±0.12(2σ) | baseline0 = 本 run 起点，非永久锚 |
| 轮内聚合 Elo (SE≈347.5/√N) | `league.py:111` | 多对手相对强度 | N=16 → ±87 Elo | 非传递（石头剪刀布）下失真 |
| 逐局 K=32 Elo | `elo.py:17` | 联赛调度信号 | 1σ≈±40 且**饱和** | 不可当强度用 |
| Bundle 合法率 | `evaluate.py:274` | 非法部署占比 | 计数级、近无噪 | 自对弈下退化 |
| Next-Card Acc/Brier/ECE | `evaluate.py:279` | 信念校准 | N=500 稳定 | 观测词表缺口时整体失真 |
| 行为指标 `behavioral_metrics` | `train_solo.py:254-408` | 接敌率/响应率/幽灵动作/组波/满费 | — | **仅 record_replays 时算，从未落盘（已复核）** |

**已验证的两个具体缺陷（已复核 + 口径修正）**

1. `runs/economy_10e/solo_state.json` 的 `history` **前两条都是 `step:0` 且数值完全相同**。
   机制（复核后修正）：`train_solo.py:867 history.append(stats)` 不按 step 去重，
   而 `:897 if cfg.eval_at_start and start_step == 0: eval_and_write(0)`
   → 同一目录**多次启动/以 step 0 续训**就会重复写点
   （旁证：`runs/` 下存在 `economy_10e_launch.log` / `launch2` / `launch3`）。
   → append 前按 step 去重即可。

2. **行为指标已计算但无门禁**（口径修正，子代理原话"从未落盘"不准确）：
   `behavioral_metrics`（`train_solo.py:254`）在 `:490` 已并入 `stats`，
   因此**自 2026-09-10 起主曲线已落盘**（10e 是 9-09 的 run，早于该改动，所以它的
   `history` 里没有——这是时间差，不是 bug）。**真正残留的缺口是**：
   ① 对照组显式 `record_replays=False`（`:841-846`）→ 对照组无行为指标；
   ② 指标只记录、**不设阈值、不报警** → 无法防止回归（AGENTS 那些
   "接敌率 7.4%→10.5%"的结论仍不是自动门禁）。

**待复核（子代理报告，未独立验证）**
- `train_solo` 的评估**无换边**（`_pair_seed_offset` 只在 `run_league.py:322`），
  自对弈中 main 恒为 P0 ⇒ 地图/先手偏置混进 0.5 零点。**建议优先核实**，若成立是
  与"2σ 噪声"叠加的第二大偏差源。

### 2.2 四个结构性盲区

1. **无绝对锚点**：所有指标都是"相对某个会变的对手"。词表 v2 事件（10d 的 1.000
   曲线里对手是"隐形人"）如果有一个固定外部锚点就会立刻报警。
2. **非传递性未建模**：Elo 假设传递，CR 卡组是石头剪刀布。需要一个"最佳回应"式
   报告（谁克谁）而不是单排名。
3. **能力退化无检测**：热启动/重训后没有"旧能力保留"探针，只测得出"比起点强"。
4. **统计功效与目标不匹配**：想检测 5% 胜率/100 Elo，但用 ±25% 分辨率的尺子。

### 2.3 改进方案（按性价比）

| 优先级 | 措施 | 成本 | 收益 |
|---|---|---|---|
| **P0** | `behavioral_metrics` 每次评估落盘并设硬阈值门禁（接敌率 ≥9.5%、幽灵动作 ≤10%） | 几乎为 0（只改落盘+比较） | 行为爬坡可自动守门，防回归 |
| **P0** | `n_eval_games` 16→40 + **换边配对**（正反手各 N/2） | 每评估 5× 时长 | 2σ 从 ±0.25 → ±0.16，消除先手偏置 |
| **P1** | **固定锚点基准集**：每轮固定对 (a) 随机初始化 (b) 固定 SelfDefenderPolicy+四卡组 (c) 上代最佳 ckpt，落盘 `anchor_state.json` | 3×40 局 ≈ 2min | **跨版本可比**；10d 式退化立即可报警 |
| **P1** | 能力保留探针：热启动后跑上代 skill-probe（法术闸门合规率等） | 低成本 | 检测遗忘 |
| **P2** | 非传递评估：PFSP 多对手胜率矩阵 + 环检测，报"最佳回应" | 每对 ≥48 局 | 正确排序 |
| **P2** | 修 10e 重复 `step:0`；`history` 加 `side`/`seed` 字段 | 极小 | 可复现性 |

**功效参考（子代理 MC 实测）**：检测 100 Elo 需 48 局/对（2σ）或 95 局（80% 功效）；
检测 5% 胜率需 800 局（2σ）或 1,568 局（80% 功效）。

## 3. 训练步数预算

### 3.1 已完成训练量换算（已复核目录与日志）

| run | 步数 | 对局数≈步/360 | 实际出牌(~8%) | 墙钟 |
|---|---|---|---|---|
| economy_9j (100k) | 100,000 | ~278 | ~8k | 14.1 h（含 GPU 崩溃 + 冷启动评估，不代表稳态） |

### 3.2 吞吐（子代理实测 + AGENTS 存档）

- 引擎+掩码+观测：**18.8 ms/步 = 53 决策帧/s**（`env.step(STOP)` 4000 帧 = 75.2s）
- NN 前向：**7.13 ms/步**（`act()`，含 CNN+主 GRU+6 步自回归子 GRU，1.41 MFLOP）
  → **模型只占约 10%，90% 耗在纯 Python 战斗仿真**
- 训练循环（含 PPO 更新）：**14.4 步/s**（10d 实测）；`--n-envs 4 --parallel mp` ≈ ×2.6 → 37 步/s

| 墙钟 | 乐观 14.4/s | 中性 8/s | 悲观 2/s |
|---|---|---|---|
| 1 h | 4.8 万 | 2.8 万 | 0.7 万 |
| 8 h | 38 万 | 22 万 | 5.7 万 |
| 24 h | 115 万 | 66 万 | 17 万 |
| 一周 | 810 万 | 465 万 | 120 万 |

### 3.3 数据效率

PPO 为**单 epoch、on-policy、无回放**（`update_interval=128`，批次 128 条过渡，
π 与 V 各更新一次）；每步至多产 1 条过渡（硬上界，已有哨兵测试）。
**无经验复用**，仅权重热启动 + 对手池提供多样性 → 样本效率显著低于多 epoch / IL 方法。

### 3.4 对标（口径：1 决策帧 = 1 obs = 1 次动作选择）

| 参照 | 量级 | 本仓库当前占比 |
|---|---|---|
| Atari CNN+PPO | 10M–50M frames | 100k = **0.2%–1%** |
| 小型确定性 sim + 低维 obs 的 PPO 常见收敛 | 0.5M–5M 决策帧 | 100k 在其下沿之下 |
| FirstLight（AGENTS 引用，25M 动作 IL 底座） | 25M | 100k = **0.4%**（等价在线 PPO ≈ 480h 单 env） |

### 3.5 结论：训到多少步

| 档位 | 步数 | 依据 | 算力（中性 8/s） |
|---|---|---|---|
| 最小可验证 | **200k–300k** | 当前 100k 行为指标仍在爬坡（接敌 7.4%→10.5%），先越过评估噪声再谈收敛 | 7–10 h 单 env / 3–4 h mp=4 |
| **目标** | **500k–1M** | 落在同类 sim 的收敛带；**前提是先修 1.1–1.4 的机制问题**，否则纯堆量边际收益低 | 17–37 天单 env / 6–13 天 mp=4 |
| 收益递减点 | >2M | 胜率 100k 已平台、行为增速随步数放缓；纯 PPO 边际≈0 | >74 天单 env |

- **100k 够不够**：对胜率不够（已平台期）；对行为质量**远未收敛**。它是起点不是终点。
- **1M 值不值**：仅当配套机制修复后才值。
- **要不要 10M**：不值（纯 PPO 算力 ~150 天、收益递减）→ 改走 IL/BC 底座 + 推理时浅 MCTS
  （AGENTS 已证推理搜索极便宜：0.19s/次搜索、一局多花 ~70s）。

### 3.6 提效优先级
1. `--n-envs 4–8 --parallel mp`（≈×2.6，接近免费）；
2. 评估降频降本（`steps_per_eval` 4000→8000，`eval_workers=16` 默认开）；
3. 卡组课程 + 组波奖励（直接攻 1.2 的根因，比堆步高效）；
4. 非镜像对手池（四卡组已落地）；
5. 经验复用：BC/IL 底座或多 epoch 回放，打破"1 transition/步"硬上限；
6. 观测降维（grid 32KB/条是 NN 前向主因）。

  → ×4 = 2,364,476，差 8,788 字节（0.37%，pickle 字典/张量头开销）✓ float32 单权重

- `solo_opt.pt` 含张量 1,258,743 = 2 × 629,359 → 确认 Adam 状态 ≈ 2× 参数 ✓

### 4.3 推理成本
单次 `act()` ≈ **1.41 MFLOP**，CPU 实测 **7.13 ms/步**；训练循环每步预算 69ms
⇒ 网络仅占 ~10%，**吞吐瓶颈是纯 Python 引擎，不是网络**。

### 4.4 容量判断：**不是瓶颈**

- 0.63M 参数承担的是"跟随者"角色，物理（`threat_calc`/`spell_module`）与规划
  （58 维 plan token）已被外部化，策略只需回答"何处/何时落子"，映射空间比原始感知窄得多。
- 容量分布病态：**单层线性 `enc_fc` 占 55.6%**，而 GRU 仅 128 维、实体 embedding 仅 8 维（0.2%）
  → 缺实体间关系建模（巨人 + 火法支援、克制链），这是**表征短板而非规模短板**。
- 实测对比：Atari DQN(2015) 约 1.7M，本模型不到其 40%。

**建议**：优先级 = 奖励设计/样本效率（1.1–1.4）＞ 表征（实体注意力、加深 enc、GRU 128→256
支撑 360 步长程信用分配）＞ 轻度扩容。**先别盲目加宽 CNN**——吞吐被引擎主导，扩容提不了步速。
