# 逐帧信用分配提案评估（2026-09-18）

> **触发**：用户方案 ——「以**局面**为基准划分，每个局面结束做一次分数结算，之后对每个**决策帧**打分；
> 评价标准 = ①放的这张牌之后造成了多少伤害 ②打死了对面价值多少圣水的牌 ③**它被当作索敌目标/被攻击时**，

## §0 结论（两栏 + 一句建议）

| 维度 | 判决 | 一句话 |
|---|---|---|
| **性能** | **可接受，但改动面比看起来大得多，且有一处会静默改游戏语义的陷阱** | 在线账本本身 ≪1% 墙钟（每帧 O(实体数)）；真正的成本是 **35 个伤害调用点 + 实体身份入快照 + 4 个共享训练入口**，以及 **`source=` 是语义参数（会让 Ronin 开始格挡法术）**；**反事实读法 = 2~5× 墙钟，不可行** |
| **效果** | **作为奖励：不接受。作为仪器/教师：值得做** | ①提案最独特的那一半（按圣水价值给击杀账）**已经在跑**（`edw` Φ，占奖励 29.84%）；②「差分/去基线」的可动空间**已被实测压到 ≈0.03（在线口径最好 +0.0344）**，单跑不可判决；③助攻项是**引擎决定**的 → 正是本仓明令"不做"的**假归因**；④瓶颈不在结算侧（全帧圣水≥6 = **0.11%**） |
| **建议** | **不改奖励**，先做 **S1 零成本门禁** → **S2 仪器化（uid + 独立 `attrib=` 通道）** | 只有当 S2 显示该量与非自引用 Elo 相关、且 S1 判"约束在结算侧"时才做单变量 A/B（且必须是**守恒式重分配**，不是加项+阈值） |

## §1 这个提案与我此前被否掉的"打分器"提案**不是同一件事**

必须先把这件事说清，否则会误判为"重走已否证的路"。

| | 旧提案（2026-09-14 深夜，`reward_settlement_v3_design` §9） | **本提案** |
|---|---|---|
| 分数怎么来 | **训一个打分器** `F(局面) → 分` | **手写事件归因规则**，分数 = 引擎事件（伤害/击杀/圣水价值） |
| 被否的理由 | ①四类输入已在网络里（`observe()["elixir"/"hand"/"grid"]` + 563 维 belief）；②potential 形式不改最优解；③**直接打分形式"没有合法分数来源"**（三条来源全堵：博弈结果=已死的 critic、现行奖励=自监督循环、外部教师=本仓没有）；④唯一可证伪的一半实测 `EV_within` = **−0.2225**（MLP，阳性对照 +0.2710 证明不是容量问题） | **本提案不涉及"学"** —— 分数来源就是引擎事件，**第③条对它不成立**。⇒ 它**逃过了**旧提案的致命否证 |
| 但它落进另一族 | — | `reward_settlement_prereg` §4 的 **E-C「反事实结算」**（"只结算本帧动作引起的增量"，状态 = 第三，成本 ×2，且**前提已被否证**）+ `rl_reward_plan_v2` 的 **P3「不造反事实假账」**（后成【R11】） |

**真正新增的三件东西**：①**归因对象**（把账记给"出这张牌的那一帧"，而不是事件发生的那一帧）；
②**助攻项**（当肉盾被索敌时，队友的输出记给肉盾）；③**阈值差分**（"有足够价值才加分"）。
下面按这三件分别判。

## §2 效果评估

### E1 ★ 提案最独特的那一半**已经在跑**（且是 potential 形式 = 不改最优解）

用户要的"打死了对面价值多少圣水的牌"，在 `edw` 资源账里**已经是实现**：

- `docs/rl_reward_plan_v2.md:137` — `Φ(s) = edw(t) × [ (手牌圣水 + Σ 存活部署单位/建筑 × 部署费) − 对方同款 ]`
- `docs/rl_reward_plan_v2.md:140` — `**单位死亡**：V −c → 我方 Φ −c·edw（送死有代价）` ⇒ **反向 = 对方单位死亡 ⇒ 我方 Φ 上升 c·edw**
- `docs/rl_reward_plan_v2.md:142` — `**法术**：无持久实体 → 施放记成本，效果（击杀返还对方 V）在效果期窗口内配对结算`

而它的份额是五项里的**第二大**：`docs/reward_composition_verdict_2026-09-14.md:37` —
`| **edw**（资源账 ΔΦ） | 383.67 | **29.84%** | ...`。

⇒ **两条推论**：
1. **提案的增量只剩**（a）账记到哪一帧、（b）助攻、（c）阈值 —— 不是"新增一种信息"。
2. 现有 `edw` 是**势函数一阶差分** `edw·[Φ'−Φ]`（`src/clasher_new/rl/env_wrapper.py:245-253`），
   按 Ng et al. 1999 **近似 policy-invariant** ⇒ 它今天几乎**不改变最优解、只削方差**（这也是它的设计意图，见 `rl_reward_plan_v2.md:98-104` 的 P1/P4）。
   **本提案若"加项+阈值"，就是把这个原本中性的项改造成非中性的目标项** —— 性质变了，不再是"结算方式"问题。

### E2 「差分」的两种读法，后果完全不同（这是本提案最关键的分叉）

| 读法 | 数学后果 | 本仓实测 |
|---|---|---|
| **A. 守恒式重分配**（同一笔账换个帧记；Σ 不变） | 目标**几乎不变**（只在 γ<1 的折扣上差二阶）；改的纯是**信用分配** | 与 §9.1 的 potential 判据同族：`max\|G' − (G − S_t)\| = 9.14e-07` ✅（`reward_settlement_v3_design:282`，仪器 `probe_gae_kernel` §H） |
| **B. 加项 + 阈值**（"足够价值才加分"） | **改变目标本身**：策略会去"待在能刷分的局面"而不管能不能赢；且阈值是**非线性/不连续**变换，GAE 消不掉它 | §9.1 原文判定：`策略会去"待在打分器喜欢的局面"而不管能不能赢（刷分/僵持）`（`reward_settlement_v3_design:291`） |

**"做差分"若指 A，是可行方向；若指 B，落进已知病理。**
而"A"的有效性上界**已被实测压住**（见 E3）。

### E3 ★「去基线/差分」的可动空间已被实测压到 ~0

这是本仓 2026-09-14 那天最有价值的三个读数（全部在固定 npz、可复现）：

| 读数 | 值 | 出处 |
|---|---|---|
| 帧间 lag-1 自相关 | **+0.987**（中位 0.990） | `reward_settlement_v3_design:38`（D5） |
| 128 帧窗口方差分解 | **窗口内 7.7% / 窗口间 92.3%** | 同上 `:39`（D6） |
| 在线口径最好的状态基线 | 19 维手写特征 窗口协议 **+0.0344**；因果滚动 **−0.0567**；高维 `fused`/`raw_obs` 因果 **−0.19 ~ −0.31** | `reward_settlement_prereg:252-255` |
| "去掉 DC/基线"对优势的实际位移 | `ΔA = +0.0330` vs `std(A) = 14.6846` ⇒ **0.22%**（换成整局均值量级也只有 **1.5%**） | `reward_settlement_prereg:241-243` |

⇒ **"差分"这一半能动的量 = 局内那 7.7% 的一小部分**（最好的在线实现 ≈ **0.034**，约 3.4%），
**远在【R5】的单跑分辨率之下**（同 seed 两次 run 不可复现；结构层仪器自身散布 ±4~8pp，见 `reward_settlement_prereg:200-206`）。
⇒ **结论：这部分必须有"同批配对 + 多 seed"设计才可能读出东西，单跑 20k 读不出来。**

### E4 ★ 助攻项 = **假归因**，正是本仓明令"不做"的那一条

用户第三条标准「**被当作索敌目标或被攻击时**，其他己方卡牌造成了多少伤害」——
本仓在 2026-09 就对"效果期窗口归因"写过判决，原文（`docs/rl_reward_plan_v2.md:79`）：

> `效果期窗口结算则**假归因**（把本来就会发生的伤害记给法术）→ 诱导"打架时乱放软控蹭账"。`

并且明文列入不做清单（`docs/rl_reward_plan_v2.md:169`、`:303`）：

> `| 软控（冰冻/藤蔓） | **不做事件归因**（反事实，P3） | 价值靠示范 + critic + 随后真实事件回流 |`
> `- ❌ 给软控手工事件归因 shaping（反事实假账，P3）`

**助攻项与"软控归因"在结构上同型**：被记功的那张牌**不需要做任何事**，只要"站在前面被索敌"。
更糟的是**索敌是引擎每 tick 重算的规则**（`src/clasher_new/battle.py:1174` `current_target = self.update_current_target()`），
⇒ 这张牌"被当作目标"的**大部分由引擎规则决定，而不是由那个决策帧的动作决定**
（决策只选"放在哪一格"）。**把一个主要由引擎决定的量记给一个决策 ⇒ 只加方差，不加可学信号。**

而本仓已有的行为取证显示，策略**最不缺的就是"往前放便宜单位"**（`docs/reward_settlement_v3_design:220`：
`费 ≤3 的 5 张卡占出手 **95.47%**`）⇒ 助攻项会**强化已经过度的行为**。

### E5 瓶颈错位：结算层不是当前瓶颈（本仓已判）

`docs/reward_settlement_v3_design_2026-09-14.md:219-222`（§6 原文）：

> `**策略几乎从不进入"攒费"状态**：全帧圣水 ≥6 仅 **0.11%**（100860 帧里 111 帧），`
> `而 6 费赢牌手段 Xbow 出手 **3/9806（0.03%）**；费 ≤3 的 5 张卡占出手 **95.47%**。`
> `⇒ "攒费 → 打 Xbow"这条链在**数据上几乎是零覆盖** ⇒ on-policy 探索失败。`
> `**任何信用/结算改动对"从未访问过的状态"都无从作用**。`

⇒ 在一个**从未访问过**的状态上，无论账记给哪一帧、有没有阈值，都没有可分配的东西。
同一节还给出互补读数：92.3% 的方差在**窗口间** ⇒ 优势里绝大部分是"局面水平差"，
**能跨局面泛化的东西不是结算口径**。

### E6 run 模式特有风险：固定脚本对手池 ⇒ "刷分"可自洽

当前主线是 `--mode run`，对手是 **5 个固定的 mask-随机脚本 agent**（`AGENTS.md` §2.1）。
在这个池子上，"造成伤害 / 击杀圣水价值"与"赢"的相关性由**固定对手的强度**决定。
⇒ 风险：策略可以**在这个池子上过拟合刷分**（拖长局面、换血刷价值），
而 **J3 的 Elo 也会同时上升**（同一个池子）⇒ **看起来像进步**。
⇒ 若要跑，判据必须用 **J3 的非自引用 Elo + 皇冠/局时长**，**不得**用新项自己的值当成功指标。

## §3 性能评估

### P1 在线账本本身的成本：可忽略

- 逐帧账本 = 每决策帧 O(实体数) 次簿记（实体数 ≈ 十几个~几十个）；
  对照预算：run 模式纯训练 **27.4 步/s ≈ 36.5 ms/决策帧**（`AGENTS.md` §3）。
- 内存：整局（≤360 帧）的事件列表是 KB 量级 ⇒ 不是瓶颈。
- **结论：如果只算"多一个 dict 记账"，性能没问题。问题全在下面 P2~P6。**

### P2 ★ 引擎侧改动面：伤害归因**当前覆盖率只有 ~1/3**

本次实测（复算命令见 §6）：

```bash
cd src/clasher_new
grep -rn "take_damage(" battle.py core.py card_mechanics.py | grep -v "source=" | wc -l   # 35
grep -rn "take_damage(" battle.py core.py card_mechanics.py | grep -c "source="          # 17
```

- `src/clasher_new/battle.py:550` — `def take_damage(self, amount, delayed=False, source=None, pierce_invincible=False)`
  ⇒ **返回值是裸 `return`，不携带 (source, target, amount) 三元组**；调用方拿到 `None`。
- `src/clasher_new/battle.py:564` — `if source is not None: self.last_hit_by = source`
  ⇒ source 只落进**单槽**字段，会被任意带 source 的伤害覆盖（不是账本）。
- **35 处不带 source 的调用点**里包含用户方案最需要的那些：建筑普攻（`battle.py:1354`）、
  投射物溅射（`:1666`）、`deal_area_damage` AoE 主干（`:3361`）、AreaEffect 法术 pulse（`:1876-1881`）。
  ⇒ **"法术/群体伤害打死了对面多少圣水的牌"目前**在引擎里**根本没有攻击者身份**。

### P3 ★★ 陷阱（本次评审最重要的单点发现）：`source=` **是语义参数，不是日志参数**

`src/clasher_new/battle.py:565-571`：

```
        # —— M7：受击钩子（Ronin 格挡反击等经 entity_holder.on_take_damage 挂载）。
        if hasattr(self.entity_holder, 'on_take_damage'):
            if self.entity_holder.on_take_damage(amount, source):
```

`src/clasher_new/card_mechanics.py:695-713`（Ronin 格挡）：

```python
    def on_take_damage(self, amount, source):
        """受击钩子（Entity.take_damage 调用）。返回 True = 本次伤害被格挡（引擎短路）。"""
        ...
        if not hasattr(source, 'data') or not hasattr(source, 'take_damage'):
            return False          # ← source=None 时走到这里 ⇒ 不格挡
        ...
        return True               # ← 返回 True = 本次伤害被吞掉
```

⇒ **为了"让 AoE/法术/建筑可归因"而在那 35 处补 `source=`，会让 Ronin 开始格挡法术/溅射伤害**
（`source` 一旦非 None 且是对面实体，就会 `source.take_damage(...)` 并 `return True` 吞掉伤害）。
**这是静默的玩法改动**，不是加日志 —— 直接违反【R2】的"默认逐位回旧"精神与【R7】的尺度对账要求。

**唯一的干净做法**：新增**独立通道**（如 `take_damage(..., attrib=None)`），
`attrib` **只喂账本**，**绝不**传给 `last_hit_by` / `on_take_damage`；
并配一道**对账 battery**：同一 seed 下 `attrib` 开/关，**奖励序列、胜负、掩码位图逐位相同**（【R13】精神 +【R8】跨局边界）。

### P4 身份缺失：**现有回放做不到精确归因**

- 快照实体是 **10 元组，无 id**：`src/clasher_new/rl/replay.py:85-90`（`[name, x, y, hp, player, kind, max_hp, shield, shield_max, radius]`）；
  `src/clasher_new/battle.py:228-241` 的 `to_dict()` **也不含 id**（同文件里实体**有** `self.id`，只是没进快照）。
- 本次实测（`runs/long1m/replays/league_88000.pkl`，50 局 / 9079 帧）：
  **8584/9079 帧（94.6%）存在重复 `(name, player)`**，多余实体 **24514** 个
  ⇒ 两个 Minions / 三只 Bats 之间**无法区分**，"谁打死了谁"在离线回放上**不可恢复**。

⇒ **离线版（零训练成本那条路）必须先给实体加 `uid` 并进快照**（`replay.py` schema 从 3 升版，只对新 run 生效）。
好消息：训练本身**已经在写回放**（`runs/long1m/replays/` 现 12+ 个文件、每个 8~12 MB），所以"多一个离线分析入口"的边际成本低。

### P5 反事实读法的成本：不可行

若"差分"是**反事实差分**（"没有这张牌会怎样"）：

- 单次浅推演实测 **43.3 ms**（`reward_settlement_v3_design:369-373`，仪器 `probe_search_cost.py`；
  纯引擎 16,635 battle-steps/s）⇒ 每帧一次 = **≥2× 墙钟**；每张候选牌一次（`K_MAX=4`）= **~5×**。
- 且它的前提**已被否证**：E-C 需要"能在线得到状态基线"，而
  `reward_settlement_prereg:258-261` 实测**在线口径全部 ≤ 0（最好 +0.0344）** ⇒ E-C 已降级为**条件项**。

## §4 圣水价值口径必须先定"单一来源"（【R7】）

**不能**用 `entity.data.get('manaCost')` 直接当"打死它值多少圣水"：
法术产物、克隆、墓园、亡语召唤（如 Night Witch 的 Bats）都不是"花这些圣水放出来的"。

引擎里**已有**这套约定，就在 `edw` 的 V 账里（`docs/rl_reward_plan_v2.md:19` 原文）：

> `死亡注销、spell 产物份额 0（防双算）；克隆/墓园等延迟/法术产物体免费；`

⇒ 新项**必须复用同一个映射/函数**（`Σ存活部署实体·部署费` 的口径），否则同一场战斗里会存在
**两套"圣水价值"**，这是【R7】"尺度改动必须单常量源 + 对账 selftest"的教科书违反。
代价口径参考：`src/clasher_new/card_utils.py:227` — `self.elixir = self.data.get('manaCost', 0)`。

## §7 用户澄清后的修订判决（2026-09-18 同日，★ 本节部分推翻 §2）

> **触发**：用户澄清三件事 ——
> ①**目的不是最优解，是收敛速度**：「为了让模型更快收敛，例如 1 费小骷髅通过拉扯即可解掉 4 费小皮卡，
> 3 费加农炮或者弓箭手搭配戈仑冰人拉扯即可解掉 7 费大皮卡」；
> ②**助攻/被索敌时长要买的就是"拉扯"**：「弓箭手放置的讲究，冰人放置的讲究，甚至**冰人从始至终打不出一点伤害**」；
> ③**「差分」的新定义 = 按卡牌价值的净交换**：进攻侧「我们后排 3 费 + 前排 3 费 = 6 费，
> 对方处理我们这 6 费花了 6 费或更多（**但对面不能 6 费全部返场**），或者手中关键牌被迫打出 ⇒ 正影响」；
> 防守侧「我们 6 费解决了对方 6 费或以上的进攻，**或者防守后留下一些卡牌返场** ⇒ 正影响」。

### 7.0 我要先认账：§2 用错了判据口径（部分作废）

| 上一轮的说法 | 修订 |
|---|---|
| §2 把「是否改变最优解」「是否假归因」当**主要**判据 | **收窄**：目标既然是**收敛速度**，主判据应是"**是否给了一个原本为 0 的信号一个非零、且随决策变化的梯度**"，而不是"是否改变最优解"。改变最优解 = 需要门禁（§7.6），不等于不要做 |
| §2 E1「击杀圣水账已在 `edw`，所以没有增量」 | **部分作废**：见 §7.2 —— `edw` 只在**以击杀/残值告终**时给钱；**"被阻止的伤害"永远 0（甚至为负）** |
| §2 E4「助攻项 = 假归因，落 P3 不做清单」 | **保留但降级**：P3 当年把这条**明确交给了 critic + 示范**去学（`rl_reward_plan_v2:169`：`价值靠示范 + critic + 随后真实事件回流`）——而**critic 是常数**（`value` 唯一值 1/600，`MLP0` ReLU 存活率 0）、**示范也没有**。⇒ **本仓为这个问题选的路已经失败**，用户提案是在补一个**已确证无人管**的缺口。上一轮把它当成"重走已否证的路"**不公平** |

### 7.1 ★ 精确化：现在到底缺哪一格信号

把"拉扯成功"分成两种结局，结论完全不同：

| 结局 | 现在的奖励 | 缺什么 |
|---|---|---|
| **拉扯 → 对面单位被打死**（如骷髅拖住、塔+弓手打死小皮卡） | **`edw` 已经给钱**：击杀敌方 4 费 ⇒ 对方 `V` −4 ⇒ 我方 Φ +4 ⇒ 奖励 `+4×edw(0.5) = +2.0`。**信号存在** | 只差**记账帧**（记在"小皮卡死亡帧"而不是"骷髅放置帧"）。实测上界 = 128 帧窗口内方差 **7.7%**（`reward_settlement_v3_design:39`）；GAE 半衰期 53 帧（`:40`），放置→死亡通常 <30 帧 ⇒ 权重损失 ≈33%，**不是零** |
| **拉扯 → 拖住/换节奏，没打死**（皮卡被引走、回头、或换路） | **全 0**：塔血没掉**不产生任何正奖励**；而冰人/骷髅被吃掉 ⇒ 对方 `V` 不变、我方 `V` −2 ⇒ **Φ −2 ⇒ 奖励 −1.0**。⇒ **正解被现行奖励"记为负"** | **这才是真空白**，并且**不是归因问题，是信息缺失**。用户点出的「冰人从始至终打不出一点伤害」正命中这一格 |

⇒ **判决修订**：§2 的"没有增量"**站不住**。真正没有增量的是上半格（记账帧，上界 7.7%）；
**下半格（被阻止的伤害 / 节奏）是本仓从未有过的新信息**，且它只能靠**代理**（真反事实要 43.3 ms/次推演，见 §3 P5）。

### 7.2 但新定义的「净交换」有一个必须指出的性质：大部分是**已有 Φ 的重新开窗**

用户定义的三项与 Φ 的对应关系（`docs/rl_reward_plan_v2.md:137/139/140/142`）：

| 用户的项 | 现状 |
|---|---|
| 「我方花了 3+3=6 费」 | 已在 Φ：deploy 段实际花费（含 Mirror/MergeMaiden） |
| 「对面 6 费不能全部返场」 | 已在 Φ：死亡注销 `V −c` |
| 「防守后留下卡牌返场」 | 已在 Φ：`Σ 存活部署实体 × 部署费` |
| 「对面处理我们花了 6 费或更多」 | Φ **隐含**（对方 deploy 花费），但见 §7.4 —— **在 run 模式下这半边是噪声** |
| 「**被阻止的伤害**」（塔血保全 / 冰人白嫖） | **Φ 没有**（塔血不进 Φ；防止伤害不产生事件）⇒ **唯一的新信息** |

⇒ **净交换 ≈ 窗口内的 `−ΔΦ`（再补塔伤保全项）**。所以本提案的工程量应当**集中到两处**：
**①窗口化 + 阈值**（有实测上界 7.7%）、**②塔血保全 / 节奏这一项新信息**（真增量）。
其余部分**不引入新信息**，不要为它付昂贵代价（尤其不要为它去改引擎的伤害归因，见 §3 P2/P3）。

### 7.3 三个必须先定义的东西（否则方案不可复算）

| # | 问题 | 建议 |
|---|---|---|
| 1 | **「局面」怎么划分**（"每个局面结束结算一次"——本方案最关键的未定义量。会重叠：双路同时开战、单位进出） | 用引擎**每 tick 的索敌关系**做**并查集**（`battle.py:1174` `update_current_target()` 每 tick 重算 target）⇒ **局面 = 目标关系图的连通分量**；分量**分裂或清空**即结算。成本 `O(E·α(E))/tick`（E≈十几个），**天然分路**、确定性、**可复现**（满足【R4】"判据必须脚本复算"） |
| 2 | **阈值形态**（"有足够价值才加分"） | 硬阈值会在边界造悬崖（策略会学"贴着阈值打"）。建议**平滑 hinge** `max(0, Trade − θ)` 或 `tanh(Trade/τ)`。θ **必须在本实验量纲上标定**（【R15】不许跨实验照抄、不许用"1 费"这种直觉值当阈值，【R16】不许单次观测标定） |
| 3 | **圣水价值口径** | 复用 Φ 的映射（**法术产物份额 0、克隆/墓园等免费**，`rl_reward_plan_v2:19`），**不要**另建一张 `manaCost` 表 ⇒ 否则同一局里出现两套圣水价值（【R7】违反） |

### 7.4 ★★ 实测：run 模式的对手**不是"会应对"的对手** ⇒ 三个例子在当前主线上没有可学样本

本次实测 `runs/long1m/replays/league_88000.pkl`（50 局，step 88000 的评估点）：

| 量 | 实测 |
|---|---|
| 平局 | **0**（winner 0:24 / 1:26） |
| 终局皇冠 | side0 = 3 冠 **25 局**、side1 = 3 冠 **24 局** ⇒ **约 49/50 局是一方打满 3 冠的碾压局** |
| 局长 | min **70 帧（35 s）** / 中位 **168 帧（84 s）** / max 450 帧（225 s，加时） |
| 对手部署 | `opp_played` 非空 **643/9079 帧**（≈13 次/局） |

对照 `AGENTS.md` §2.1：run 模式的 5 个对手**均 mask-随机**脚本。两条推论：

1. **「对方花 6 费来解我们」在 run 模式里不是一个"应对"，是噪声。**
   随机脚本不会因为你的推进而"被迫打出关键牌" ⇒ 净交换里**对方花费那一半测的是噪声**；
   好消息是**我方净效率 / 返场那一半仍然有意义**（决策相关）。
2. **拉扯技能需要"会组织推进的对手"**。1 费骷髅解 4 费小皮卡、冰人+弓手解 7 费皮卡，
   前提是对面**真的在推一次皮卡**。mask-随机脚本不推 ⇒ **这个技能在 run 模式里没有可学样本**。
3. 顺带：run 模式局长中位 **84 s ≈ 168 帧 ≈ 1.3 个 `update_interval`**（128）⇒ episode 本来就已经
   **又短又决绝**，"信用传得太远"**不是 run 模式的主要瓶颈**；主要瓶颈是**对手质量**。

⇒ **判决：这套奖励要挂在 `solo`（对手 = 冻结副本 / hist 池 / SelfDefender，是目标导向的）上，
不要挂在当前的 `run` 主线上。**（若坚持在 run 上做，则只应取"我方净效率/返场"那一半。）

### 7.5 助攻项要生效，有一条硬性规格：**"其他己方卡牌"必须包含公主塔/国王塔**

否则用户举的**第一个**例子直接失效：1 费骷髅拉扯小皮卡时，**伤害主要来自塔**。
若"其他己方卡牌"只算单位，骷髅拿到的是 **0 分**。⇒ 规格：助攻池 = `我方单位 ∪ 我方建筑（含公主塔/国王塔）`。
（这也是"被索敌时长"能变成信号的前提：塔在打它，而它把对方钉在塔的射程里。）

### 7.6 失败模式与门禁（可证伪，须写进判据）

**净交换最大化 ≠ 赢**：可以"交易赢全场、比赛不进攻"。这正是
`reward_settlement_v3_design:291` 命名的病理：`策略会去"待在打分器喜欢的局面"而不管能不能赢（刷分/僵持）`。
**指纹（可测）**：**局时长 ↑、超时局占比 ↑、皇冠数 ↓ 而交换值 ↑**。
⇒ 两道门禁任选其一（建议都加）：
1. **转化门**：只在"交换优势在 N 秒内转化为塔伤/皇冠"时才给分；
2. **行为门禁**：把**局时长 / 超时率 / 皇冠数**列为判据（相对本 run 首点退化 ⇒ 判失败）。
⚠️ 当前 run 模式**观测不到**这个风险（0 平局、49/50 三冠碾压）；**换到 solo 就会暴露**，
所以门禁必须在 **solo 实验**里写死。
