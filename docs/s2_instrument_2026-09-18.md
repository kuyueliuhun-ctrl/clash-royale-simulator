| 交战对 | 跨边 ∧ 至少一侧非产物（规则①） | §1 |

| 净交换 | `Trade_me = ΔΦ_me − ΔΦ_op + tower_term_me` | §2.1 |
| 窗口基线 | 取 **`t0-1` 帧**的边界状态（= 窗口第一次动作**之前**） | §2.1（两形式等价的必要条件） |
| `tower_term` | 六种代理（`none/p3a/p3b/p1/p2/p4/p4b/p5/p5b`）全实现，默认 `p4` | §2.2 + 本文件 §5 |
| 分数化 | `score = max(0, Trade − θ)`，`θ = 1.0` | §2.3 |

**三个必须在实现里定死、而预注册没写的口径**（都登记进 §8）：

1. **窗口身份判据**：默认 `identity=core`（交战核心 = 参与交战对的**非塔**实体）。
   用"全成员"会把「同一座塔被不同单位先后攻击」粘成一个 **span=247 帧**的窗口（规格字面读法**不可用**）。
2. **`tower_term` 的零和性**：默认 `tower_transfer=zero-sum`，且**两侧各自视角对称化**
   `term = [(τ₀ − τ₁)/2, (τ₁ − τ₀)/2]`。只算 p0 视角再让 p1 取负 ⇒ 另一半局（main 坐 player 1）
   拿到的 `τ ≤ 0`，**相关性被系统性偏置压成 0**（实测踩到，见 §8.3）。
3. **`tower_term` 只统计本局面成员**：否则同一个死亡会被所有重叠窗口各记一次（重复计数，§8.5）。

## §3 出口判据 ①：`Trade` 的方差地板与分布

**数据**：`runs/run100k/replays/` 的 **schema-4** 录像
（`league_0.pkl` 100 局 + `league_8000.pkl` 50 局，run100k 的评估点，`run` 模式）。
口径：`K=1`、`identity=core`、`phi_mode=component`、`recon=costname`、`tower_mode=none`。

| 量 | 实测（`league_0`，100 局） |
|---|---|
| 局面窗口 | **10,861 个 / 100 局 = 108.6 个/局** |
| 窗口跨度 | 中位 **2 帧**，p25 2，p75 2，max **198 帧**，均值 6.30，σ 13.37 |
| 结算原因 | `split_or_vanish` **78.9%** / `merge` 18.4% / `episode_end` 2.0% / `no_engagement_K` **0.8%** |
| `Trade_p0` | min −13.35，p25 **0.00**，中位 **0.00**，p75 **0.00**，max +13.50，均值 −0.04，**σ = 2.06**，MAD 0 |
| 局级 `ΣTrade` | σ ≈ **13.15**，均值 +3.08，min −25.40，max +60.47 |
| `score>0` 的窗口 | **14.6%**（`θ=1.0`） |
| **独立对账残差** | 全局口径 `\|净支出(原始圣水) − ΔΦ\|`：n=**10,861**，中位 **0**，均值 +0.01，σ 0.05，max **0.71** 圣水 |

**读法**：

1. **分辨率**：局级 `ΣTrade` 的 σ 是 13.15，`n=108` 个窗口 ⇒ 局级均值的标准误 ≈ **0.20**。
   要在**单局**上分辨 1 圣水的效应，需要 ≈ `(1.0/0.20)² ≈ 25` 局（同一对手）；这与【R5】一致。
2. **零膨胀**：`p25 = p75 = 中位 = 0` ⇒ 绝大多数窗口的 `Trade` **恰好为 0**（没有部署、没有死亡、
   也没有塔伤）。⇒ 有效统计量是"少数非零窗口"，不是 108 个独立样本。
3. **★ `K` 是死参数（本数据上）**：`K ∈ {1,2,3,5,10}` 的读数**逐位相同**
   （窗口/局 108.6 / 108.5 / 108.5 / 108.5 / 108.5；σ(Trade) 2.09→2.10；ρ 完全相同）。
   原因：窗口几乎总是因为**交战双方都死了/清空**而结束（79% `split_or_vanish`），
   不是"临时断开"。⇒ **预注册 §1 的"连续 K tick 无交战对"在本回放分辨率下不可辨识**，
   任何关于"去抖"的论证在本数据上**是空的**。`K=30 tick` 仍按"有原则的选择"保留，但**不得**当作已标定参数引用。

## §6 出口判据 ④：与非自引用结果的相关性

**为什么要专门写一节**：这条判据**在实现中被两个口径 bug 连续污染过**，若不查就会得出**假结论**。

| 结果量 | 定义 | 备注 |
|---|---|---|
| 皇冠差（main 视角） | `crown_opp − crown_main`（**注意方向**，见 §8.4） | 与塔血差 ρ ≈ +0.68（自洽） |
| 终局塔血差（main 视角） | `Σ塔血_main − Σ塔血_op` | 连续量，**主用** |
| 胜负 | `winner == main_player` | ⚠️ run 模式 **96/100 胜** ⇒ **几乎没有方差**，本批数据上**不能当判据** |
| ~~终局 Φ 差~~ | `Φ_main − Φ_op` | **自引用**（`Trade` 由 `ΔΦ` 构成）⇒ 只作 sanity |

**实测（见 §4 表）**：

- `none`（不加项）：ρ(塔血) 在 5 批上 = −.092 / −.027 / −.141 / **+.098** / **+.280** ⇒ **符号不稳**。
- `p3b`（预注册首选）：ρ(塔血) = −.025 / −.029 / +.009 / +.068 / +.340 ⇒ **也不稳**。
- `p4b`：ρ(塔血) = **+.052 / +.056 / +.101 / +.200 / +.430**（5/5 正，单调随样本量增大）。
- `p1`：ρ(塔血) = **−.268 / −.322 / −.227 / −.284 / −.518**（5/5 **负**）⇒ 接线方向与目标相反。

⇒ **出口判据 ④ 的判读**：**没有"已出相关性"**；`p4b` 是唯一方向稳定（5/5 同向）的候选，
但幅度（0.05–0.43）**未超批间散布**（§4 末表）。
**并且**：run 模式的**胜负方差几乎为 0（96/100）** ⇒ 用胜负当判据在本数据上**不可行**，
这与评审 §7.6 的警告一致（必须换 `solo` 才有失败模式可观测）。

### 7.1 身份判据：按"全成员"重叠 ⇒ 出现 span=247 帧的"局面"

`landmark`：初版按连通分量的**全成员**重叠续接。塔（id ≤ 6）恒在场上 ⇒
**任何"同一座塔被不同单位先后攻击"都会续接成同一个窗口**，实测出现 span = **247 帧（123 s）**的"局面"
（852 个窗口里 max=247、σ=16.4）。这不可能是"一个局面"。
⇒ 改为 `identity=core`（交战核心 = 参与交战对的**非塔**实体），塔仍计入 `members_union`（信用归属要用，§7.5）。

### 7.2 去抖 `K` 是死代码（初版）+ 后续仍**不可辨识**

初版在**不活跃帧**把"该分量的匹配键"设为核心 = 空集 ⇒ 无重叠 ⇒ 窗口**立刻**结算 ⇒
`no_engagement_K` 结算占比 **0 / 2174**，`K` 完全是死代码。修掉后占比升到 **0.8%**，
但**§3 的敏感性扫描显示 `K ∈ {1,2,3,5,10}` 读数逐位相同** ⇒ 在本数据上
**"去抖"这个机制不可辨识**（窗口是因为交战方全死而结束，不是临时断开）。
⇒ **登记：`K=30 tick` 保留为"有原则的选择"，但任何"去抖有效"的论证在本数据上无效。**

### 7.3 ★ 零和"对称化"只算 p0 视角 ⇒ 另一半局被系统性扣分

初版 `tower_transfer=zero-sum` 实现为 `term = [+τ, −τ]`，其中 `τ` **只按 p0 视角算**。
但联赛**每一场对阵打两局、双方互换**（`meta["side0"]` 标明谁坐 player 0）⇒
当 main 坐 player 1 时，它拿到的 `tower_term` 是 `−τ_p0 ≤ 0`，**与它自己做了什么无关**。
后果：**相关性被系统性偏置压成 ≈ 0**（修正前 ρ(胜) 全在 ±0.08，修正后候选才显出 5/5 同向）。
⇒ 改为两侧各自视角再对称化：`term = [(τ₀ − τ₁)/2, (τ₁ − τ₀)/2]`（既零和又对称）。
**对照臂 `own`**（旧行为）保留在 CLI 里，供复算这个偏差。

### 7.4 ★ `crown` 字段的方向（`get_crown_count` 返回的是"让出去的皇冠"）

`player.py::get_crown_count()` 数的是**本方被拆掉的公主塔**
（`int(self.left_tower_hp <= 0) + int(self.right_tower_hp <= 0)`），
所以 `battle_snapshot` 里的 `crown0/crown1` 是**该方让出的皇冠**，不是拿到的。
用错方向 ⇒ `ρ(皇冠差, 塔血差)` 从 **+0.92** 变 **−0.92**（符号全反，而两个结果量本该高度自洽）。
⇒ 实现里明确取 `crown_opp − crown_main`，并在 `analyze_game` 写了注释。
**这条对全仓其它消费 `crown` 的脚本都适用。**

### 7.5 `ΔΦ` / `tower_term` 的重复计数

- `phi_mode=global`（预注册 §2.1 的**字面读法**）在**双路同时开战**时会把同一笔账计入多个窗口
  ⇒ 实现默认 `phi_mode=component`（只统计窗口成员），并把 `global` 作为对照臂保留。
- `tower_term` 初版扫描**全场**死亡 ⇒ 同一个死亡会被所有重叠窗口各记一次；
  修成**只统计本局面成员**（`members_union`）后，`league_0` 全量上 `p3a` 的 `τ` 均值
  从 **1.64 降到 0.38**（同期窗口口径也变过，故只作**量级指示**，不作精确归因）。
  ⇒ 即：**P3 的"信号"里有 ~3/4 来自重复计数**。这是一条会直接推翻 §4 结论的 bug。

## §11 局限（【R10】如实写）

1. **所有读数基于 `run` 模式**（对手 = mask-随机脚本）⇒ 评审 §7.4 的结论仍适用：
   **拉扯没有可学样本**，本文件的 ρ 只说明"仪器能算"，**不能**说明"策略能学"。
2. **schema 4 的两处退化**：`is_product` 缺失 ⇒ 规则①**恒真**（"纯产物互殴"也会被当交战对）；
   `V` 靠**离线重建** ⇒ 帧内延迟出兵/建筑产物可能污染份额（已用 `recon=costname` 缓解并计数）。
   **重建法本身尚未在真实数据上对过账**——schema 5 落地后才能做（§9）。
3. **`tower_term` 的 P3 家族只承认"钉住→打死"**，P4b 用"窗口内我方三塔零掉血"当门控——
   这是**代理**，不是反事实（真反事实要 43.3 ms/次推演，训练不可用）。
4. **未做**：优势兑现率门禁、`solo` 数据、奖励项接线、默认关对账。
5. **`N=100`/`n=50` 的 ρ 判读**已按 `1σ` 标注；**没有做多重比较校正**，9 个代理 × 3 个结果 = 27 个 ρ
   ⇒ 单个 |ρ| < 0.3 的"发现"在 5 批里出现一两次**可能只是噪声**（这正是 §4 用 5 批同向性而不是单批显著性的原因）。
