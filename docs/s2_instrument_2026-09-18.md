## §1 仪器口径（与预注册的对应关系）

| 概念 | 实现 | 依据 |
|---|---|---|
| 索敌关系图 | 每一帧用 `a.target_id == b.id` 建无向边（用实体 `id` 为键） | §1 |
| 局面 | 该图的**连通分量**（并查集） | §1 |
| 交战对 | 跨边 ∧ 至少一侧非产物（规则①） | §1 |
| 结算 | 连续 `settle_frames` 帧无交战对 / 分裂 / 合并 / 清空 / 局末 | §1 |
| 残值 `V` | schema ≥ 5 取**帧内在线真值**（`v0`/`v1` + 每实体 `share`）；schema 4 **离线重建** | §2.1 |
| 净交换 | `Trade_me = ΔΦ_me − ΔΦ_op + tower_term_me` | §2.1 |
| 窗口基线 | 取 **`t0-1` 帧**的边界状态（= 窗口第一次动作**之前**） | §2.1（两形式等价的必要条件） |
| `tower_term` | 9 种代理（`none/p3a/p3b/p1/p2/p4/p4b/p5/p5b`）全实现 | §2.2 + 本文件 §4 |
| 分数化 | `score = max(0, Trade − θ)`，`θ = 1.0` | §2.3 |
| 门禁 | 优势兑现率（`N = 20 s`、`θ` 门限），`scripts/offline_engagement_trade.py` 内置 | §5.1 第三行 |

**四个必须在实现里定死、而预注册没写的口径**（都登记进 §7）：

1. **窗口身份判据**：默认 `identity=core`（交战核心 = 参与交战对的**非塔**实体）。
   用"全成员"会把「同一座塔被不同单位先后攻击」粘成一个 **span=247 帧**的窗口。
2. **`tower_term` 的零和性**：默认 `tower_transfer=zero-sum` 且**两侧各自视角对称化**
   `term = [(τ₀−τ₁)/2, (τ₁−τ₀)/2]`。
3. **`tower_term` 只统计本局面成员**。
4. **`Trade` 的口径**（★ 影响结论）：默认 `phi_mode=global` = **预注册 §2.1 的字面读法**
   （`ΔΦ` 取整块场地）；`phi_mode=component`（只算窗口成员）作为**保守对照**，两者**都要读**（§4、§6）。

## §3 出口判据 ①：`Trade` 的方差地板与分布

**数据**：`runs/run100k/replays/` 的 **schema-4** 录像（`league_0.pkl` 100 局 = 5 对 × 20 局 × 2 侧）。
口径：`K=1`、`identity=core`、`recon=costname`、`tower_mode=none`。

| 量 | `phi_mode=global`（**主口径**） | `phi_mode=component`（保守对照） |
|---|---|---|
| 局面窗口 | **10,861 个 / 100 局 = 108.6 个/局** | 同 |
| 窗口跨度 | 中位 **2 帧**，p25 2、p75 2、max **198**，均值 6.30，σ 13.37 | 同 |
| 结算原因 | `split_or_vanish` **78.9%** / `merge` 18.4% / `episode_end` 2.0% / `no_engagement_K` **0.8%** | 同 |
| `Trade_p0` | min −11.06，p25 **0.00**，中位 **0.00**，p75 **0.00**，max +12.35，均值 −0.02，**σ = 1.84** | σ = **1.50** |
| 局级 `ΣTrade` | 均值 **+13.67**，**σ = 19.67**，min −23.69，max +98.35 | — |
| `score>0` 的窗口 | **12.9%** | **5.3%** |
| **独立对账残差** | `\|净支出(原始圣水) − ΔΦ\|`：n=10,861，中位 **0**，均值 +0.01，σ 0.05，max **0.71** 圣水 | （同左，恒等定义） |

**读法**：

1. **分辨率**：局级 `ΣTrade` 的 σ 是 19.67，`n=109` 个窗口 ⇒ 局级均值的标准误 ≈ **0.19**；
   要在**单局**上分辨 1 圣水的效应需 ≈ 105 局 ⇒ 与【R5】一致（单 run 只能看大效应）。
   本文件全部相关性都是**局级 + 配对**，正是为了绕开这个分辨率限制（【R16】）。
2. **零膨胀**：`p25 = p75 = 中位 = 0` ⇒ 绝大多数窗口 `Trade` **恰好为 0**（无部署、无死亡、无塔伤）。
   ⇒ 有效统计量是"少数非零窗口"。
3. **★ `K` 是死参数（本数据上）**：`K ∈ {1,2,3,5,10}` 的读数**逐位相同**（窗口/局 108.6→108.5；
   σ(Trade) 2.09→2.10 的旧记录在修缺陷 6 后同样不变；ρ 完全一致）。原因：窗口几乎总是因为
   **交战双方都死了/清空**而结束（79% `split_or_vanish`），不是"临时断开"。
   ⇒ **"连续 K tick 无交战对"在本回放分辨率下不可辨识**；`K=30 tick` 保留为"有原则的选择"，
   **不得**当作已标定参数引用。任何只依赖 `K` 取值的结论都**不成立**。
4. **两口径的差别是"跨路流量"**：`score>0` 从 5.3%（component）到 12.9%（global）——
   component 口径只算窗口成员，**别路的下牌/死亡不进本窗口**；global 口径按预注册字面读法取整块场地。
   `phi_mode=global` 的代价是**双路同时开战时同一笔账会落进多个窗口**（§7.5），
   所以下文**两种口径都报**。

## §5 出口判据 ③：「钉住但没打死」的占比（缺口实测）

口径：**"被非塔实体钉住"** = 窗口内存在敌方实体，其跨边对手里有 `id > 6`（非塔）的实体。
（宽口径"任意跨边含塔"恒为 100% ⇒ 没有分辨力，已弃用。）

| 量 | `league_0`（100 局，`none`，global） |
|---|---|
| 有"被非塔实体钉住"的窗口占比 | **30.8%** |
| 其中**零死亡**（钉住但没打死） | **66.8%** |
| ⇒ 占全部窗口 | **20.6%**（2235 个） |
| 这些窗口的 `Trade_p0` | min −11.00，**p25 −1.00**，中位 **0.00**，p75 +0.18，**均值 −0.36**，σ 2.13 |

**判读**：**缺口成立且被量化**——约 **1/5 的窗口**是"成功钉住但没打死"，
它们的 `Trade` **中位数为 0、均值为负（−0.36）、p25 = −1.00 圣水**。
这正是评审 §7.1 下半格与用户「冰人从始至终打不出一点伤害」所指的那一格。
量级上：实测均值 **−0.36**，比评审举例的"−2 费（−1.0 奖励）"**小**（那是单实例上界）
⇒ **引用时应引用本文件的分布读数**（【R10】）。

### 6.3 ★ 判读：S2 的相关性门禁**算过了**（配对口径）
- 预注册 §9 的门是"S2 未出相关性别开 S3"。**现在就配对判据而言，相关性是出的**：
  同批 5/5 同向、幅度跨批一致（§4.2），且**不依赖 `phi_mode`**（10/10，§4.3）。
- **但**这不是预注册 §5.1 意义上的"判决"：§5.1 要求阈值在**本实验自己的量纲**上、
  按"前 100 次诊断更新的中位 ± 3×MAD"标定（【R15】【R16】），本步**没有**做那个标定

## §7 ★ 实现中发现并修掉的 6 个规格/口径缺陷

> 每一条都会让一个"看起来有结论"的读数变成错的。**第 6 条直接改变了 §4/§6 的结论**，
> 本文件全部读数已按修好的仪器重算（第一版读数作废，见 §7.7）。

### 7.1 身份判据：按"全成员"重叠 ⇒ 出现 span=247 帧的"局面"
塔（id ≤ 6）恒在场上 ⇒ 任何"同一座塔被不同单位先后攻击"都会续接成同一个窗口
（实测 span = **247 帧**）。⇒ 改为 `identity=core`（交战核心 = 参与交战对的**非塔**实体）。

### 7.2 去抖 `K` 是死代码（初版）+ 后续仍**不可辨识**
初版在不活跃帧把匹配键设为核心 = 空集 ⇒ 窗口**立刻**结算 ⇒ `no_engagement_K` 占比 **0/2174**。
修掉后升到 **0.8%**，但 §3 的敏感性扫描显示 `K ∈ {1,2,3,5,10}` **读数逐位相同**
⇒ **"去抖"在本数据上不可辨识**。

### 7.3 ★ 零和"对称化"只算 p0 视角 ⇒ 另一半局被系统性扣分
初版 `zero-sum` 实现为 `term = [+τ, −τ]`，`τ` **只按 p0 视角算**。但联赛**每场打两局、双方互换**
（`meta["side0"]` 标明谁坐 player 0）⇒ main 坐 p1 时拿到的 `tower_term` 是 `−τ_p0 ≤ 0`，
**与它自己做了什么无关** ⇒ 相关性被系统性偏置压成 ≈ 0。⇒ 改为`[(τ₀−τ₁)/2, (τ₁−τ₀)/2]`。

### 7.4 ★ `crown` 字段的方向（`get_crown_count` 返回的是"让出去的皇冠"）
`player.py::get_crown_count()` 数的是**本方被拆掉的公主塔**，所以 `battle_snapshot` 的 `crown0/1`
是该方**让出**的皇冠。用错方向 ⇒ `ρ(皇冠差, 塔血差)` 从 **+0.92** 变 **−0.92**。

### 7.5 `ΔΦ` / `tower_term` 的重复计数
- `phi_mode=global` 在**双路同时开战**时会把同一笔账计入多个窗口（预注册字面读法的代价）⇒
  默认口径保留 `global`（规格优先），但必须与 `component` 两读。
- `tower_term` 初版扫描**全场**死亡 ⇒ 同一死亡被所有重叠窗口各记一次；
  修成**只统计本局面成员**后，`p3a` 的 `τ` 均值从 **1.64 降到 0.38**（同期窗口口径也变过，
  只作**量级指示**）⇒ 即：**P3 的"信号"里约 3/4 来自重复计数**。

### 7.6 ★★ 组件口径把**别路的下牌花费**算进本窗口（**本文件第一版读数的致命伤**）
`ΔΦ` 形式的圣水部分是**整块场地**的（`elixir0/1` 是全局字段）而残值部分是**窗口成员**的
⇒ 只要窗口期间我们在**别的路**下了牌、且那笔兵**在窗口内死了**，那笔花费会被算进本窗口
却拿不到对应的 V 记入 ⇒ 窗口 `Trade` 被系统性压成负数。
**实测**：一个"敌方 3 费白给、应记 +3"的窗口被算成 **−1**。
⇒ 组件口径改为走 §2.1 的**净支出形式**（两侧都是成员口径，自洽，且不需要 `regen`）。
回归测试：`test_component_phi_excludes_other_lanes`。

### 7.7 第一版读数作废声明（【R10】只增不改）
第一版（缺陷 6 未修）给出的表格与结论**作废**，此处不改历史：
- 第一版 `league_0`：σ(Trade) = 2.06、`score>0` = 14.6%、`p4b` ρ(塔血) = +0.161、ρ(胜) = +0.251；
- 第一版结论"p4b 幅度未超批间散布（0.14 < 0.16）"**在配对口径下被推翻**（§4.2：配对 5/5 正）。
- 第一版把 `none` 当作"ρ≈0 的对照"；**修好后**在主口径下 `none` 均值 +0.124（5/5 正），
  在组件口径下 4/5 负 ⇒ `none` **不是**一个中性的零点，这一点现在被明确写出来。
> 如需复现第一版：`git show 9ec022f:scripts/offline_engagement_trade.py`（不推荐，有已知缺陷）。

## §11 局限（【R10】如实写）

1. **所有读数基于 `run` 模式**（对手 = mask-随机脚本）⇒ 评审 §7.4 的结论仍适用：
   **拉扯没有可学样本**，本文件的 ρ 只说明"仪器能算"，**不能**说明"策略能学"；
   run 模式胜负方差≈0（96/100）⇒ 胜负列**单用不可判**。
2. **schema 4 的两处退化**：`is_product` 缺失 ⇒ 规则①**恒真**（"纯产物互殴"也算交战对）；
   `V` 靠**离线重建** ⇒ 帧内延迟出兵可能污染份额（`recon=costname` 缓解并计数）。
   **重建法尚未在真实数据上对过账**——schema 5 落地后才能做。
3. **`tower_term` 全是代理**，不是反事实（真反事实 43.3 ms/次推演，训练不可用）；
   `p4b` 的门控"窗口内我方三塔零掉血"是**代理**。
4. **未做**：阈值标定、`solo` 数据、奖励项接线、默认关对账、跨局边界指纹。
5. **多重比较**：9 个代理 × 3 个结果 = 27 个 ρ ⇒ 单个 |ρ| < 0.3 的"发现"可能只是噪声。
   这正是本文件改用**配对 5 批同向性**而不是单批显著性的原因。
6. **§4.2 的配对结论有一个已知的替代解释**：`p4b` 的 `τ≠0` 出现在 14–20% 的窗口上，
   它把"我方三塔零掉血"的门控加进去，等价于**给"没挨打的窗口"加分**——
   而"没挨打"与"终局塔血高"天然相关。⇒ 这与"它学到了被阻止的伤害"**不可区分**，
   两者要分开必须靠 S3 的行为层判据（部署节奏/推进），本文件无法区分。
