## §1 在线实现（`rl/engagement.py` + `rl/env_wrapper.py` + `rl/config.py`）

| 项 | 实现 |
|---|---|
| 局面 | 每 **engine tick** 在存活实体上按 `current_target` 建无向图 → 并查集连通分量 |
| 交战对 | 跨边 ∧ 至少一侧非产物（规则①；`is_product` 由记录通道提供） |
| 身份判据 | **交战核心**（跨边上的非塔实体，`id > 6`）；窗口的 key = **最后一次活跃时的核心** ⇒ 目标瞬态丢失不会立刻掐断 |
| 结算 | 连续 `SETTLE_TICKS = 30` tick 无交战对 / 分量清空 / 局末 `flush()` |
| 净交换 | **`phi_mode=global`**（预注册 §2.1 字面读法）：`ΔΦ_x = Δ(手牌圣水 + 残值 V_x)`，`trade = ΔΦ_0 − ΔΦ_1 + τ` |
| 为何不需要逐窗口记账 | **potential 形式下"出牌"不改变 Φ**（圣水 −c、残值 +c 相消），自然回复对两侧相同也相消 ⇒ 基线取哪一 tick 都行 |
| `τ` | **P4b**（§11.7.1 逐字）：`gate × Σ_E cost(E) × min(1, 钉住秒数/T_ref)`；`cost(E)` 取在线 `_v_share`（**产物体恒 0** ⇒ 绝不估值）；`gate` = 窗口内我方三塔零掉血 |
| 零和 | `trade_opp = −trade_me` 由构造保证；`score = max(0, trade − θ)` 两侧各自铰链 |
| **默认关** | `engagement_trade = 0.0` ⇒ `RLEnv.__init__` 里 `self._et = None`，**不构造对象、不做任何 tick 工作、不加任何浮点运算**（【R2】） |
| 成本 | 每 tick 一次并查集（E≈15）；**只在开关打开时发生** |

开关（`rl/config.py::DEFAULT_REWARD`，**全部默认关/中性**）：
`engagement_trade = 0.0`（权重）、`engagement_trade_theta = 1.0`、`engagement_trade_t_ref = 2.0`、
`engagement_trade_gate = 1`。

> **已知缺口（如实记）**：`RLEnv.step` 只在 `battle.game_over` 时 `flush()` 局末仍开着的窗口；
> 若上游按 `max_ep_steps` **截断**（`RLEnv` 恒返回 `truncated=False`），尾部的开窗口**不会结算**，
> 其 score 丢失。离线仪器是会在 `episode_end` 结掉的 ⇒ **两边在最尾部有一处不对称**。
> 处置：要么给 trainer 加一次显式 flush 调用，要么把它登记为已知损失（尾部窗口占比未测）。

## §2 开/关逐位对账（预注册 §6 的 battery）

工具（新增）：`scripts/s2_trade_probe.py`，用法 `python s2_trade_probe.py <tree_dir> <off|on>`。
它驱动 `RLEnv` 跑一段**确定性脚本局**（60 决策帧、30 次出牌，双方交替），
对每个决策帧累计：奖励、全部实体的 `(id, 存活, hp, x, y, target_id)` ⇒ 一个 SHA-256。

| 树 / 开关 | REWARD_DIGEST | REWARD_SUM | 在线 `ET_N` |
|---|---|---|---|
| **真树（未打补丁）** | `4d8b27b839af7bbddd7af754ee383aa7540bf0b96d3188b1f475bf5b448eca0c` | −7.118533323 | —（无该字段） |
| **sandbox（打了补丁、开关关）** | **`4d8b27b8…eca0c`（逐字相同）** | −7.118533323 | 0（对象未构造） |
| sandbox（开关**开**） | **`4d8b27b8…eca0c`（仍相同）** | −7.118533323 | **2** |

**读法**：
- 前两行 = **默认关逐位回旧**（R2）✅ —— 奖励序列与全部实体状态逐位相同。
- 第三行 = 打开开关后**奖励仍相同**，原因是 `trade = 1.0` 而 `θ = 1.0` ⇒ `score = max(0, 1.0 − 1.0) = 0`
  （两个窗口各 +1.0）⇒ 项值恰好为 0。**这说明铰链在 θ 处确实连续**（不造悬崖），
  也说明这段合成局的交易量太小、不足以展示非零项 ⇒ **开路径的"非零"证据要等真实局的 measure-only 跑**（§6）。

## §3 ★ 在线 ↔ 离线：同一局，切分口径差了 30 倍

把 §2 那段**在线跑出来的录像帧**（含帧内 `v0/v1`，`exact=True`）交给**离线仪器**重算同一局的局面：

| 口径 | 窗口数 | Σtrade | Σscore |
|---|---|---|---|
| 离线 `identity=core`，`settle_frames = 1 / 2 / 3 / 5 / 10 / 20` | **67（六档完全相同）** | +1.00 | **+8.00** |
| 离线 `identity=members` | 6 | +0.13 | 0.00 |
| **在线（K=30 tick、tick 级索敌图）** | **2** | +2.00 | 0.00 |

### 3.1 为什么
- **分辨率**：在线每 **tick** 看一次索敌图（30 tick/决策帧），交战双方在同一 tick 内持续互相索敌；
  离线每 **决策帧** 才采样一次，帧与帧之间的索敌可能已经换人 ⇒ 采样到的"交战核心"**逐帧不相交** ⇒
  `identity=core` 被切碎（67 个窗口 ≈ 每帧一个）。**这不是实现 bug，是采样分辨率差。**
- **`K` 在两边都几乎不生效**：离线 `settle_frames` 从 1 调到 20 结果**一字不变**，
  因为窗口几乎总是死于**分量清空**（交战单位死了）而不是"临时断开"；
  在线同理（`rep not in hits`）。⇒ 预注册 §1 的"连续 K tick 无交战对"这条规则**在真数据上很难被触发**，
  与上一轮在 100 局真实录像上的结论一致（`no_engagement_K` 只占 0.8%）。
- **`identity=members` 更接近在线**（6 vs 2），因为塔恒在场上把分量黏住；但它在真实录像上会退化
  （上一轮实测 span = **247 帧**的"局面"）⇒ **不能简单换成 members 来对齐。**

### 3.2 结论（**推翻上一轮的"可以放行 S3"**）
> 上一轮基于离线 `identity=core` 得到的配对结论（`p4b − none` 的 Δρ 5/5 正）**只对
> "帧采样微局面"这个口径成立**；奖励项实际使用的是**tick 级、K=30 tick** 的切分
> ⇒ **两者不是同一个量**（同一局 Σscore 差 8.00 vs 0.00）。
> ⇒ **S2 的证据不足以放行 S3**。要放行，必须用**在线口径**重测：
> 让评估局以 **measure-only**（跑监视器但权重为 0）跑，把**在线窗口的 `trade/score`** 落盘，
> 再在**同一批局**上做与上一轮相同的配对 ρ 分析。
>
> 这条与 S1 的判定**互相独立**：S1 说的是"约束在探索/机制侧"（Xbow 自锁），
> 本条说的是"S2 的证据口径与奖励口径不匹配"。**两条都指向：先别开 S3。**

## §4 受控落地与一次 **CRLF 假阴性**事故（【R10】如实记）

第一遍执行 `scripts/_apply_s2_channel_when_idle.sh` 时：

```
[05:43:15] === 验证 1/3：行为中立性逐位对账 ===
[05:43:16] !! DIGEST 不一致：9adc2aafee52aa55f964fb52af7ac86fc240d105058d880bb50772b95bcd5b55
DIGEST 9adc2aafee52aa55f964fb52af7ac86fc240d105058d880bb50772b95bcd5b55
[05:43:16] !! 回滚
```

打印出来的 digest **就是期望值**，脚本却判"不一致"并**回滚了一次正确的补丁**。原因：

> Windows 版 python 的 stdout 在**重定向到管道/文件**时是 **CRLF**；
> `awk '/^DIGEST/{print $2}'` 取出的最后一个字段带**尾随 `\r`**（`od -c` 实测末尾是 `\r`）
> ⇒ `[ "$D" != "$EXPECT_DIGEST" ]` 必然成立 ⇒ **假阴性**。

修法：`... | awk '/^DIGEST/{print $2}' | tr -d '\r'`。第二遍执行即通过（§5）。

**教训（与仓库里"PS 5.1 无 BOM 按 GBK 解码"同一类）**：**跨 WSL/Windows 边界做逐字节比较时，
必须先剥掉 CR**；否则失败会指向"补丁有问题"，而真正的问题是取值方式。
⇒ 已写进脚本注释；这条与【R1】"先归因外部"同源：**失败先怀疑测量链路，再怀疑被测对象。**

1. §2/§3 的对局是**合成脚本局**（60 帧、30 次出牌、对手为内置随机）⇒ 只能证明**机制通路**与
   **口径分歧**，**不能**代替真实局的统计。

3. `τ`（P4b）在合成局里**全为 0**（没有"被非塔实体钉住"的样本）⇒ §3 的 Σtrade 差异完全来自
   `ΔΦ` 部分的切分差异，**不是**对 `τ` 的验证。
4. 在线监视器**只实现了 p0 视角**；`flow` 模式的 p1 镜像路径（`rl/flow_league.py`）**未接**
   ——按预注册 §7-1，镜像侧应取 `−score`，但**尚未实现也未测试**。
5. §3.1 的"分辨率"解释是**读码 + 单局对照**得出的，**未做多局统计**；结论方向明确（67 vs 2），
